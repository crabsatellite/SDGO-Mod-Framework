# 公共测试数据维护

只在统一本地 test 缺少必要场景数据时使用。日常测试绑定已有账号和已有机体，不注册新账号，也不重新创建整套环境。

## 初始数据

统一 test 从本机生产客户端、服务端和一致的数据库副本复制，保留其中已有账号和资产。复制在线数据库时使用原生一致备份恢复到独立实例；不能直接复制正在写入的 MDF/LDF 后假定完整，也不能让副本继续连接生产 SQL。此初始化只做一次，之后持续复用。

已有五账号及公共机体声明由 `tools/game_test_fixtures.py` 维护。原模板常用机体为 `10003,22040,22042,22097,24402,24787,24788`；账号槽位 1/2 曾分别用于阿普萨拉斯 24788/24787 对照。**实际账号和 UID 以当前 test 数据库及私有绑定为准**，不得把旧模板 UID 或真实玩家 UID 写死在测试代码。已有代码和有效检查结果继续继承。

本地 test 尚未包含所需资产时，先查已有账号的库存、战舰、合法编组、默认出击机体和操作员；优先选择已满足场景的账号。不要调用 `build_accounts` 或旧 Docker `environment template/upgrade` 去重新注册、整库还原。

## 如何增加必要数据

1. 确认当前连接的 SQL 进程、实例和全部可写文件都属于本地 test，列出缺失机体/资源及需要修改的已有账号。生产库不用于此操作。
2. 只给现有测试身份补场景必需的数据。机体通过原生 `GOnlineGame.dbo.sp_CreateUserUnit` 分配 UID/序列号，先查 `tbl_ItemCategory` 的 CatalogueID、RefIndex 和期限。战舰、编组、默认出击及操作员沿用原生业务存储过程和容量限制。不能复制其他玩家库存记录或任意修改 identity。
3. 保留原账号身份和已有资产，在私有绑定中更新实际新 UID；公共机体变化同步修改 fixture 声明和核验逻辑，不能关闭校验掩盖缺项。普通测试脚本不隐式维护数据。
4. 模型/资源只补进本地 test，相关代码或声明可提交 Mod 库，原始程序、游戏资产、数据库、密码和账号配置不提交。
5. 核验库存归属、原生登录/机库和受影响的真实场景。以后直接复用更新后的 test，不每次恢复数据库。并发副本完成后整套删除；成功维护/测试记录在读回后删除，保留公共 test 数据。

需要并发时，从停止且状态一致的 test 复制，或对在线 test 做一致备份后恢复到副本自己的原生实例。给副本配置独立地址、端口和数据库文件，检查所有路径后启动；绝不硬链接可写数据库，也不改基础 test 或生产数据。

# 机体族导入（Beta）

[English](unit-import.md) · [返回功能目录](../README.zh-CN.md)

在 SDGO Mod Manager 中导入机体包（RAR/ZIP），补齐缺少的定义，生成商城、扭蛋和图鉴使用的图片，
再把机体定义写入服务端，并生成给玩家安装的客户端包。

本功能处于 Beta，基本流程仍在开发。目前支持单形态和完整的双形态机体，技能只能复用服务器已有的技能。
导入的机体上线前，建议先在测试服实际出击，检查武器、技能和变形。

| 组成 | 运行在 | 负责 |
|---|---|---|
| Manager「机体导入」面板 | 服主电脑 | 解析、补齐、出图、确认和发布 |
| `unit_catalog` | 客户端 | 让游戏加载导入机体的原生记录和资源 |

通用发布包只有工具，不带任何机体。服主的草稿、图片、发布物和安装收据保存在自己的工作区。

项目也可以携带初始化脚本声明及完整程序文件。Manager 显示脚本组数量，并在导出项目时保留这些内容。
请先保存制作项目；带有新增初始化脚本的机体尚不能发布。

## 准备

打开 `SDGO Mod Manager.exe`，选择左侧「机体导入」，设置：

- **配套客户端**：与服务器配套的客户端目录。
- **制作工作区**：可选择已有 `unit-families.json` 所在的目录，保留原来的草稿、编号、发布版本和历史；
  留空时使用 Manager 工作区下的 `data/units`。
- **WorldServer INI**：留空时只做离线制作，不写游戏服务端。数据库凭据只从本地 INI 读取，不会进入玩家包。

Manager 已内置 Python、Pillow 和 pyodbc；解析 RAR 需要本机安装 7-Zip。打开面板不会修改游戏资源，也不会停止服务。

## 导入流程

1. 选择或拖入 RAR/ZIP。工具从 BIN 内部读取编号和字段，不按文件名判断机体身份。
   不支持的布局、损坏的记录、重复的身份、不完整的变形关系或缺少核心模型时，直接拒收。
2. 单形态（变形目标为零）会自动识别。双形态分别显示两种形态的属性、变形目标、武器和资源，
   由你选择进入机库的根形态。
3. 已读出的属性直接显示；缺少的服务端字段留空，不会当作 0。可以手填、上传 JSON 定义，
   或选一台原版机体作模板补齐。模板只补空项，不覆盖包里读出的数据。每个字段都标明来源，补齐后仍可修改。
4. 选择原生永久机体物品模板。工具在受管范围内分配类别号，只登记机体类别。
5. 检查依赖列表。可以单独补传 BIN、模型、动作、特效、贴图和 SPR；缺少的武器需要同时有客户端记录和服务端定义。
6. 分别为商城和扭蛋选择或上传图片，查看生成结果，见下文[图片](#图片)。
7. 保存草稿，核对生成的图标，逐项勾选后点击「确认图标并导入」。

确认会记录当前内容版本和生成图片的哈希；之后修改草稿需要重新确认。

### 在游戏里预览（可选）

点击「准备独立预览副本」「打开原生预览客户端」，正常登录后，可在游戏原生的商城机体视图和扭蛋候选中查看新机体。

- 预览副本是本模块管理的独立客户端，沿用原客户端的修复和连接配置，不会停止原游戏或服务器。
- 新机体只登记在这个副本的内存中。商城里还没有真实商品，所以只显示机体视图，不显示模板商品的名称和价格。
- 购买、赠送和扭蛋请求在预览副本中被拦截。准备预览不写服务端，也不发放机体。
- 预览副本保存在工作区的 `native-previews` 中，不要分发它，给玩家使用「玩家客户端包」。
  面板可以清理过期的预览副本，当前预览和草稿会保留。

### 图片

- **商城**：商城列表使用 122×122 的已持有图鉴图标，导入页的商品预览与它相同。
- **固定扭蛋**：卡面使用现有的卡面生成器（头像裁切、原生卡框、等级条和稀有剪影），与机台编译共用。
- **自定义扭蛋**（如 SR）：使用机体自己的候选头像，等级边框由游戏原生控件绘制，不套用固定卡框。
- **机体详情图、另一种列表图、候选头像**是三个独立的图片通道。默认沿用原生引用的图片；
  选择「由所选源图生成」后，用你的图片替换对应通道。
- **图鉴**：每个机库根形态一条目录项，带 122×122 的已持有／未持有图标；变形态不单独算作机库机体。
  没有配套设计图时，不借用模板机体的配方。

包里没有自己的图标时，借用的原版图片可能是另一台机体。可以截取真实模型的准备／选择动作
（见[开发者说明](#用-gametest-截图和核对)），上传 PNG 后切换到「由所选源图生成」。
面板里的缩略图是生成器的输出，实际效果以游戏内预览为准。

### 限制

- 主包最多 32 MiB，解包后最多 128 MiB、512 个文件；PNG 最多 8 MiB，边长 1–2048。
  路径越界、链接和重复路径会被拒绝，包内的安装程序和数据库脚本不会运行。
- 新机体 ID 与原生机体或其他已导入机体冲突时无法确认，工具不做二进制整体换号。
- 原生行为配置：单形态（`native-single-form-v1`）、互相变形的双形态（`native-linked-forms-v1`）、第二形态不再变回的
  单向变形（`native-one-way-forms-v1`）、变形目标为自身的记录（`native-self-transform-v1`），以及变入已发布双向形态之一的
  入口形态（`native-entry-forms-v1`）。入口形态是独立的库存根：第一次变形走原生双槽机制，之后在双向形态之间的往返需要
  形态图运行时——服务端 Mod 在已安装的形态图允许该边时把第三形态写入未激活的原生槽，客户端 Mod 在原生交换前把记录／模型
  对重新指向该形态。没有安装形态图授权时，服务端会继续拒绝第二跳，机体停留在双向形态的第一个形态。
- 缺少技能时默认无法确认。对技能 1、2，界面会逐个提供「移除缺失技能 … 后导入」。确认后，
  所有引用该技能的形态在客户端和服务端同时清为 `0`，原 RAR/BIN 保留，旧的预览确认失效，该技能的效果不再存在。
  其他技能、武器和变形关系不受影响。技能 3 暂不提供移除。
  第一技能移除、第二技能保留时，机体详情中的第一技能区域留空，第二技能仍由原生界面显示；
  不会把它移到第一槽，也不会补入占位技能。

### 服务端内部名与中文显示名

原生服务器的部分定义列是 `varchar`，非中文排序规则下存不了中文，因此内部名必须是 ASCII：
可以使用包里的英文名，或自行填写、从模板选择。中文显示名另存到客户端宽字符记录和 `tbl_UnitNames.NameCN`，
不会变成问号。写入时逐字段读回核对，出现截断、编码损失或外部修改时整笔回滚。

## 确认后写到哪里

- **配置了 WorldServer INI**：在一个带应用锁的 SQL 事务中更新机体、武器、名称和物品类别定义。
  工具不会重启 World/Store/Battle/Agent，请按提示正常刷新相应服务的缓存。
- **离线模式**：只登记到本工具的机体目录，生成玩家客户端包和服务端计划；界面会显示“未写游戏服务端”。

两种模式都先生成并检查发布物，再标记为已确认；SQL 失败时草稿不会变成已导入。
服务端已经提交、本地目录还没保存完时，下次启动会根据发布事务收据恢复。
发布包包含同一工作区里所有已登记的机体，新增第二台不会覆盖第一台。

导入只写非玩家定义表、本模块的所有权账本，以及启用收藏扭蛋时的机体族元数据（初始形态和变形关系，供它的实时奖池读取）。
不改玩家余额和机库，不发放机体，不替换原生 SQL 过程，也不设置商城价格或扭蛋概率。

## 设计图草稿与获取路线

制作面板支持设计图草稿，并区分原始记录、作者设定与未知字段。配方需要设计图物品、目标机体、
三到五个有顺序的材料及等级要求；第一项是原生流程保留的关键机体。原始七槽结构可以保留，
未支持的显示数量和未知必填项不会自动补零。图鉴主配方需要明确选择。

没有绑定客户端展示清单时使用内置兼容模板；设计图大图和默认卡面复用机体已选的扭蛋图像，
不沿用兼容模板机体的图片。大图使用原生 252×101 画布，从所选客户端的设计图资源恢复原版细边框和切角后自动合成；
右侧卡面使用独立的 183×87 画布，保留原生控件边框。生成资源随项目发布物一起打包，无须另行上传边框素材。
无法可靠恢复客户端边框时会明确报错。
显式指定的卡面和已审核的完整展示模板仍按各自绑定生成。

使用宿主兼容模板的结构化配方支持两端编译、受保护的定义登记及原生合成流程。
第一台材料是原生保留的关键机体，其他材料和图纸按所选服务端的规则消耗；导入定义不会向玩家发放图纸或材料。
获取路线还会检查设计图物品及材料是否确实可得。S 级及以上的库存根形态使用独立活动机；
A/B/C 级优先检查闭合的设计图路线，否则使用普通扭蛋。预览路线不会自动写入机台、价格或奖池。

## 制作项目与活动机

在「机体资料」中可先保存简介、别名、搜索示例、作品来源和图片，再补机体定义。
制作项目 ZIP 携带原图、处理后的图片和哈希；资料不依赖某台服主电脑的路径。
扭蛋面板的「机体资料与素材库」可读取这些项目，将选中的海报和资料存入当前扭蛋制作目录。
这一步只准备素材，不登记奖品或上架机台。

S 级及以上的每个机库根形态可单独生成活动机草稿。在 Manager 选择价格与奖池模板：

| 模板 | 价格参考 | 目标机体默认频率 |
| --- | --- | --- |
| 普通 G 币 | 本服设置，或普通 G 币机台的常见价格 | 本服设置，或原生参考均值 |
| 少量代币 | 本服设置，或普通代币机台的常见价格 | 本服设置，或原生参考均值 |
| 99 代币高阶 | 99 代币原生机台 | 同档奖励的原生配置均值 |

99 代币模板需明确选择，不会因为缺少同档普通机台而自动采用。
在「本服模板参数」中设置目标频率和价格，留空则沿用当前宿主参考。
这些参数只保存在服主制作目录及其导出配置中，不作为通用 Mod 的内置值。
模板根据当前宿主的原生目录生成陪奖；服主仍可调整货币、价格、机体、设计图、消耗品、数量及频率，
也可为同一物品设置不同数量的奖励。每次套用模板会预填表单，保存前可继续修改。
没有合适原生参考时会提示补充配置，不猜测货币或技能行为。

奖池使用 10000 格整数频率，合计必须为 100%；同一类别的各数量档合计不能超过 50%。
这是原生序列的配置频率，原有随机起点、连续重复规避、限额及扣费规则继续生效。
保存会检查机体及奖品目录，随后「编译」和「导入到游戏」配套应用海报与原生服务器奖池。
客户端和服务端配置不一致时不会按独立活动机流程完成安装。
更新奖池保留已有玩家进度及原生状态表，不重置账号、不直接发物品、不替换原生抽取过程。
活动图片与奖池属于服主自己的制作项目；通用工具包不包含这些内容。

## 让玩家获得机体

**确认导入后不会自动发放机体、创建商品、定价或放进扭蛋。** 获取方式由服主配置：

- **商城**：在同一数据库的「商城商品」面板点击「刷新物品目录」，选择新机体物品，新增商品、设置售价并应用。
  只保存商品草稿还不等于上架。
- **扭蛋**：在「机体导入」点击「同步已确认机体与扭蛋头像」，再到「扭蛋机」选择机台、槽位和概率，编译并应用。
  同步本身不改现有机台、价格或概率。C/B/A 级导入机体可以放进原生自定义普通槽位；稀有槽仍按机台等级规则，
  S 级候选按 SR / SS 规则。

同步只接受已经应用到同一个游戏数据库的发布：按 `[DB Game]` 的服务器和库名判断，WorldServer 与 StoreServer 的
INI 指向同一个库即可，凭据不参与比对。离线发布、未确认的草稿、其他数据库和过期的目录版本会被拒绝。
编辑已发布的机体后，商城和扭蛋继续使用上一份已确认的内容，重新确认后才切换到新图片。
卡面生成器升级后，旧的扭蛋卡面缓存需要重新编译。

## 分发给玩家

确认后可以下载「玩家客户端包」和单独的「服务端计划」。客户端包含配套 DLL、原生记录、资源归档、公开定义和安装器，
不含服务器密码、玩家数据、日志或整套游戏文件。它只用于部署，不能再当作原始机体包导入。

玩家关闭游戏后，在 Manager「游戏功能」中选择客户端，点击「导入客户端配置包」。Manager 使用内置的安装器，
不会运行 ZIP 里自带的脚本。也可以离线安装：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Install-UnitCatalog.ps1 -ClientRoot D:/Game
```

安装器只更新本模块和清单中属于自己的资源，保留其他 Mod 与全局开关；遇到外部改动或冲突时拒绝覆盖。
卸载同样需要先关闭该客户端：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Install-UnitCatalog.ps1 -ClientRoot D:/Game -Uninstall
```

玩家需要同时安装配套机体包和更新后的扭蛋机资源。已安装的扭蛋目录较旧时，先更新框架再安装机体包。

## 停用与备份

停用会保留定义、编号和资源，不删除玩家已经持有的机体；彻底清除服务端定义需要另外做引用迁移。
已发布机体的机库根形态保持固定，避免一次编辑改变玩家已持有机体的身份。

请备份服主工作区，保留草稿、family 身份、编号和发布收据；不要用空工作区重新分配已发布的内容。

## 日志

| 日志 | 含义 |
|---|---|
| `native unit catalog registered: <n> added, <m> already present, <t> total` | 导入机体已加载 |
| `unit <id> weapon <id> is unavailable` 等 `... is unavailable` | 客户端包与游戏数据不配套，缺少引用的武器、形态或物品类别 |
| `native allocation failed ...` / `native insertion failed ...` | 原生注册失败，本次客户端会终止，避免半套机体进入游戏 |

## 开发者说明

### 构建与测试

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A Win32 -DBUILD_TESTING=ON
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure -R "unit_(catalog|preview|import|presentation)|mod_manager"
python -B tools/mod_manager.py --workspace D:/ModManager
```

开发信息视图可以指定原生快照、单独构建的 `unit_catalog.dll` 或 7z 路径。缺少组件时仍可检查和编辑草稿，
确认发布会把它列为关键缺项。

### 客户端加载

`unit_catalog` 支持 `GOnline-54BE1568-00C97000`，校验 EXE 哈希和签名。它在最后一张原生表加载后，
用原生分配器注册完整的 unit/weapon/item 记录，并检查数据树中的跨类型编号冲突。所有记录先完整预检和分配；
若部分记录写入后原生注册意外失败，原生数据树无法回滚，因此记录诊断并终止本次客户端。

游戏不会从工作目录读取新增模型。客户端包附带 `resource-overlay.ini`、`resources.zdx` 和 `resources.zpk` 原生归档，
游戏从中读取模型、动作、纹理和特效；与扭蛋目录同时启用时，两者共用同一个资源读取器。

`registrations.json` 以及 Manager 的 `/api/providers/units/api/units/registrations` 提供稳定的 `unit:<根形态 ID>`、
类别、名称、形态和同版的 `shop_sprite` / `capsule_sprite`。扭蛋机台卡面是独立资源，与机体的三个 UI 图片字段分开。

记录格式、图片字段、资源归档、事务和扩展接口见[原生机体包接口](unit-import-protocol.zh-CN.md)。

### 设计图记录与展示模板

每份配方可选绑定 `sdgo.unit-blueprint-client-templates/1` 或 `/2` 客户端展示清单。
Manager 中的服务器配方／图纸兼容模板只用于宿主兼容基线，与上传的客户端记录分开。
清单按成员路径和 SHA-256 绑定 kind 33 的1197字节配方记录、kind 34 的614字节图纸物品记录、
各自的源版本与审核后准备版本，以及全部直接引用资源。编译只改已知的编号、名称、材料、等级和关联字段，
其余字节保留；`preserve-template` 模式保留图纸物品自己的名称。缺文件或哈希不符会拒绝。
发布包给出逐记录哈希和字节差异收据。版本1验证传输与直接引用；版本2还要求
`resource_dependencies`，为准备版本 SPR 的每一帧携带对应 TXR 成员及哈希，检查原生 SPR 布局、
纹理解码和资源预算。只有准备记录引用的 SPR 及其纹理进入运行包，源版本专用记录和图片作为项目证据保留。

`capabilities.blueprints.native_registration` 表示使用宿主兼容模板的结构化配方能否登记。
完整上传展示记录另看 `capabilities.blueprints.client_templates.native_registration_authorized` 和
`native_registration_schemas`：版本2在准备资源闭包完整且验证通过后支持发布，版本1仅用于传输。

### 技能／浮游依赖与资源仓库

「原始形态关系」逐条显示完整机体记录中的有向变形目标，以及当前根形态沿这些目标可到达的路径。
多个入口共用后续形态时，不能从当前入口到达的记录仍保留并分别显示，不会自动补反向关系。
该图只说明记录引用，不推断可持有的机体、实际变形条件或运行兼容；三形态以上仍须对应适配器准入。

开发者库 `sdgo_unit_form_composition` 可在独立内存中合成当前进程的原生形态武器数据和属性。
它要求已验证的宿主符号、预期的只读目录回调及已初始化的模式数据；只复制装备加成标量，
不复制玩家对象，并保留 FP 状态和 `LastError`。合成前的武器区必须全零；已使用的武器区会被拒绝，
初始化前的属性切片单独保留。输出含借用的原生指针，不能存入制作项目，也不能在房间或目录重建后复用。
`StageInactive` 只准备独立的槽位副本，保留库存身份、血量、
技能、当前形态选择和当前武器状态。复用已缓存的目标形态还须头部、武器指针和属性切片一致，
并保留已有弹药及冷却状态。这些函数不提供安装许可或实际变形提交，
Manager 的多形态发布限制仍然生效。

`StageEquivalentInactive` 提供更受限的准备方式：完整的新建来源／目标武器数据及属性切片，
除机体编号和定义指针外必须逐字节一致；现有五个武器定义指针也须匹配。
通过后仅在独立槽位副本中准备这两个身份字段，保留全部运行字节、SP 和已修正属性。
这不证明机体／技能语义等价、安全淘汰旧形态或死亡／换机后的恢复；实际提交前仍须原生适配器闭合这些条件。

控制器请求 [`sdgo.unit-form-graphs/1`](unit-form-graphs.schema.json) 将库存入口与完整机体记录摘要绑定。
控制器在同一加锁事务中读取机体、物品定义及所有权账本；入口还须有同版、同属的机体物品登记，
只读复用原版节点则须独立的基线证明。记录标识和回滚 JSON 参与快照指纹，审计时间不参与。
原生策略库 `sdgo_unit_form_graph` 只允许从库存根实际可到达的记录所指向的有向变形边。
辅助节点保留为可检查的数据，不会自动成为可选入口。自身指向自身的记录也会保留，
但实际使用仍需要单独的行为适配。

编译器生成内容候选和独立宿主许可；后者只能由受信任的宿主控制器安装，不能进入内容包。
解析器核对两者的精确绑定和宿主版本，快照指纹只说明来源，不是对当前数据库／客户端的持续校验。
部署读回以及原生实体、代际、发送者、存活状态和房间锁检查仍需独立完成。
这些策略函数不会开放多形态发布或激活原生实体。

原生战斗定义见证由 `prepare_native_from_cursor` 在同一加锁事务内读取机体／入口快照，
并读取宿主 `tbl_UnitGradeInfo` 的等级映射，生成原有 `SDGOUF1` 内容及独立 `SDGOUA2` 宿主许可。
每个图节点都有完整的 114 字节预期数据；末尾 `+0x6A` 是 `UserGradeLimit`，
`+0x6E` 是关联等级表的 `LevelRating`，不能按机体表列顺序误写成日限／月限。
缺失等级关联会拒绝编译。其余 SQL 字段仍受完整服务端行摘要约束，v2 指纹同时绑定等级快照。
解析器核对节点覆盖、顺序、编号／有向边、数据摘要和宿主；旧版 v1 许可只支持捕获，不提供原生定义见证。
服务端的 114 字节预期数据不替代完整的 4976 字节客户端机体记录。
独立性来自控制器管理的安装路径和写入边界；摘要不是数字签名，内容项目不得写入宿主 `install-state`。

消费者使用定义前还必须对照当前原生目录数据。`MatchBattleDefinition` 仅接受原始选择器
将越界默认武器索引规范为 `1` 的变化，其余字节必须一致；分配填充和内部链表指针不属于定义数据。
预期数据或比对成功都不授予实体、有向边或生命周期权限，也不会自动开放实际多段变形。

安装 v2 宿主许可后，`unit_catalog_server` 在原始发送者验证及房间锁范围内校验已登记的人类机体变形请求。
库存 UID、捕获代际、有向边、当前目录字节及缓存定义指针须同时一致；拒绝请求沿用原始错误／解锁路径，
已缓存的合法目标继续由原始流程完成变形及通知。未受管理的机体和 NPC 保持原始路径。
该 profile 不支持运行中重建机体表，安装变化后需重启宿主。
尚未缓存的有向目标只进行检查；这一层不重绑武器数据，也不迁移技能、弹药、冷却或已发射对象状态。
v1 许可不会安装这一检查入口。

提供配套形态图输入时，`unit_catalog_server` 捕获原始人类机体构造器的初始化前种子及成功输出。
存在 `room_random` 时使用共享生命周期观察接口；不兼容或已被占用的接口会拒绝加载。
否则安装完整的原生开始、构造及释放观察范围。回调使用有界队列，由工作线程处理账目。
只有原生开始成功后才提供快照；释放或新一轮开始会淘汰旧房间代际和玩家代际，
即使指针和库存 UID 重用也不能沿用旧快照。模式 6/7 捕获全部四个机体槽。
接口故障、队列溢出、阶段不匹配及过期 token 均拒绝复用。定义指针仍属于当前原生进程，
快照有效不代表可以修改实体；发送者、原始房间锁、当前目录、血量、技能和武器生命周期仍需原生校验。
当前消费者不会提交实际变形。

`ReadNativeTransformContext` 仅用于受支持宿主的双数据区变形边界：原生已完成发送者、房间、
血量及两个定义指针检查后，读取来源 UID、所选机体槽及实体身份，以便与开始时的捕获数据比较。
返回指针只在本次原始房间锁范围内有效；头部可读不证明当前目录一致。
该读取器不支持单数据区 profile，也不授予替换武器数据的权限。

原生服务端的机体编号范围为 `10001..30000`。遇到编号冲突时，应使用机体专用重编号区间，
不能套用武器／技能的大编号池。目录计划和写入器会在更改 SQL 前拒绝越界的机体及变形目标。
重编号预览不等于编号已预约，相关资源、脚本常量和两端运行安装仍需完成。

「配套原生资料」读取项目中的
[`sdgo.unit-native-content/1`](unit-native-content.schema.json)，显示技能／浮游记录、已提供的服务端定义、
图集和待补／待适配项。可上传包含 `manifest.json` 及引用成员的 ZIP 补充资料；
「更新此组资料」明确替换所选组，保留机体／武器原始记录与此前发布，并使旧预览确认失效。

每条支持的技能／浮游记录提供「编辑服务端定义」窗口。包内已知的两端共享字段自动读取并锁定；
其余字段标为必填，可手动填写或搜索、选择完整原版模板。模板只来自配置的服务器／定义快照，
保存时核对完整行哈希及两端共享字段；不兼容模板不会用来猜值。服务端战斗模式独立填写，
不能把客户端技能的调度值复制过去。未齐的值可保存为草稿，随项目导出、重新导入后仍显示缺项；
补齐并通过类型检查后保存为完整显式定义。旧版本窗口不能覆盖新修订，原始资料和此前发布保留。

制作项目导出后重新导入仍保留原始字节、准备记录和来源证据。未知类型及调度值会保留并阻止准入，
保存资料不会自动开放运行发布，也不会产生服务端安装许可。

发布编译器会从最终发布的模型字节自动生成机体记录的模型摘要，包括改写了内部资源路径的模型，
保留原始记录和素材。

开发组件可用 [`sdgo.unit-skill-atlases/1`](unit-skill-atlases.schema.json) 准备独立技能图集。
声明与运行文件绑定完整技能记录、机体目录和资源归档；原生详情及战斗技能初始化分别沿用原有资源消费者。
此组件不会开放新增技能的普通 Manager 发布。

浮游定义使用 [`sdgo.unit-server-funnels/1`](unit-server-funnels.schema.json)，沿用技能数据的事务与所有权检查，
核对六列服务端定义及对应客户端字段。目录以 `pending_funnel_ids` 继续阻止尚未完成运行准入的定义发布。

默认关闭的 `unit_catalog_server` 配套组件读取控制器生成的技能绑定与独立服务端安装记录，
保留新增技能编号并选择受支持的原生分支。详见[原生技能身份选择器](skill-identity.md)。
组件不携带服主内容，也不会开放新增依赖的普通 Manager 发布流程。

开发者可用 `owner.units.effect_resources` 根据实际 ZFX emitter 字段准备独立的特效／纹理资源名，
区分同名资源的不同版本，拒绝覆盖已有不同字节，并保留来源与输出摘要。它支持原版 JPEG TXR
及 PNG/DDS/TGA；模型依赖需要单独适配。这个制作辅助接口尚未接入 Manager 自动导入流程，
不能代替技能登记、服务端依赖或实际出击验证，详见[协议](unit-import-protocol.zh-CN.md#特效纹理的资源域准备)。

初始化脚本声明和项目保存格式见[协议](unit-import-protocol.zh-CN.md#初始化脚本制作声明)。

开发工具的技能／浮游记录 profile 保留完整源记录。技能 profile 检查882→1132字节投影、明确换号，
以及可选的类型化关联技能换号；732字节浮游记录只允许改变编号字。原生目录检查固定长度与
机体→技能、武器→浮游、技能→关联技能的类型化引用。服务端数据和独立资源的准备并不代表
编号专用行为、脚本及所有对象生命周期都已完成准入，因此暂不能通过 Manager 发布。
[原生所有权测试](game-test.zh-CN.md#原生记录所有权与正常退出)
核对完整记录字节及原始目录清理，不覆盖战斗激活、变形、死亡和重生。

大型制作素材库可使用仅供开发的分页资源仓库读取器 `owner.units.resource_depot`。它校验固定索引、有界元数据页、
压缩分片和流式内容哈希，不把整个素材库载入内存；逻辑路径冲突时保留各个变体，复用基线和服主别名需要目标检查。
原始游戏脚本只作为数据保留，不获得执行权限。该读取器不安装资源、不登记记录，也不替代 Manager 的导入流程。

### 批量机体阵容发布（`tools/gunion/publisher`）

恢复出来的整套阵容（几百个机体族）由批量发布器一次做成一个 `unit_catalog` 包，而不是在 Manager 里逐族导入。
它分四个阶段运行，每个阶段在配置的输出目录写一份回执：

```powershell
python -B -m tools.gunion.publisher families  --config <私有配置.json>
python -B -m tools.gunion.publisher resources --config <私有配置.json>
python -B -m tools.gunion.publisher programs  --config <私有配置.json>
python -B -m tools.gunion.publisher assemble  --config <私有配置.json>
```

- **families** 按完整记录给每个机体上下文分类：单形态、互相变形的双形态、单向双形态。自变形回环和第三、第四个入口
  形态记入 `deferred_entries` 并附原因；缺模型的上下文记入 `excluded_contexts`。
- **resources** 遍历每个族的资源图（模型、动作、纹理、特效、图片、声音）：与基线相同的文件直接复用，基线没有的文件
  按原路径发布，与基线不同的文件改用带所有者哈希的别名发布，并改写所有类型化引用（记录、模型材质、特效、
  图片帧）。该目录原生读取器不会打开的扩展名（例如 `txrs` 下的 `.psd`）记为 `unsupported`，不发布。
  技能和浮游炮记录作为共享记录准备。
- **programs** 用官方 Lua 5.0 工具链编译脚本闭包（LuaJIT 转储先降级），把导出名放到所有者前缀下，绑定武器回调字段，
  并把改写后的武器记录写到 `programs/weapons/`。配置里有两类经过人工审核并记录的适配：`script_adaptations`
  （带期望次数的文本替换，用于 5.0 编译器没有的 5.1 语法）和 `callback_substitutions`（基线和发布脚本都没有定义的
  回调名；客户端把回调当作 Lua 全局量查找，缺失时只会抛出被捕获的错误，所以替换成空值即恢复引擎默认路径，
  替换成别的名字即重新绑定）。所有实际应用的适配都列在 `programs.json`。
- **assemble** 生成 `catalog.bin`（kind 2、10、11、13、20、33、34、85）、资源归档、原生脚本包、技能图集和
  `publication/package/` 下的安装包，并在旁边输出 `registrations.json` 与 `server-plan.json`。programs 回执
  比 families 或 resources 回执旧时拒绝运行。多个族共用的武器由发布顺序里第一个族拥有，其余族只引用
  （`shared_weapon_ids`），因为服务端账本每行只记一个所有者族。服务端 `varchar` 名称列写入折叠成 ASCII 的值
  （`publication.json` 的 `server_names_normalized`、`server_weapon_names_normalized`），客户端仍保留原来的宽字符名。

该包只带归档：`manifest.json` 用 `resource_overlay.paths` 声明归档条目，不带游戏从不读取的松散副本；
安装器同时接受这种布局和 Manager 的 `owned_paths` 布局。服务端先写共享的技能、浮游炮和势力行，再按族通过
普通仓库事务写入；原生服务端直接读取这些行，单形态、互相变形、单向变形和自变形的族不需要形态图或技能身份授权。

入口形态作为独立的族发布（`native-entry-forms-v1`；变入单向终态时为 `native-one-way-forms-v1`），与核心族共用目标形态：
共用形态的记录、行和名称仍由核心族拥有（`shared_form_ids`）。物品类别和每个共用武器行的所有者族都固定在回执旁的
`allocations.json` 里，重新发布不会挪动已安装族的类别，也不会把武器行换到别的族名下。对每个带入口形态的上下文，装配阶段还会写出 `form-graph-requests.json`：
每个上下文一条 `sdgo.unit-form-graphs/1` 请求，其 `families` 把核心族和入口族归入同一个形态图所有者。
可信的服务端控制器在行写入后用 `owner.units.form_graph_runtime.prepare_native_from_cursor` 编译它们，把 `form-graphs.bin`
放到 `unit_catalog_server` Mod 目录、把 `sdgo/install-state/unit-form-authority.bin` 放到每个战斗主机；
之后服务端 Mod 会把允许的第三形态写入未激活的原生槽，客户端 `unit_catalog`（`FormChains=1`）在原生交换前
把备用记录／模型改指向该形态。

### 用 GameTest 截图和核对

以下检查使用 [GameTest](game-test.zh-CN.md) 的独立测试客户端和数据库，不写真实玩家数据。
GameTest 组件的设置需要在 `prepare` 封存输入之前写好，并绑定测试账号实际持有的机体 UID。

**机体一览和详情**：在候选 stage 的 `game_test_client/mod.ini` 中启用 `UnitPresentations=1`，需要截图时再加
`CaptureNativeFrames=1`，然后：

```powershell
python tools/game_test.py prepare --client-template <local-test-client> --stage <candidate-stage> --run-dir build/game-test-runs/unit-check --target-host <test-loopback-ip> --login-port <test-login-port> --account-profile <private-existing-account.ini> --play-unit-uid <owned-unit-uid> --include-mod unit_catalog
python tools/game_test.py run --run-dir build/game-test-runs/unit-check --timeout 600
```

场景经原生登录和机库选择取得实际 UID，打开机体一览，搜索并选择对应条目，等待详情模型和变形动作。

**截取机体头像素材**：在同一 stage 再启用 `UnitPortraits=1`（保留上面两项），运行后导出：

```powershell
python -m tools.game_test_portraits --run-dir build/game-test-runs/unit-check --unit <root-unit-id> --output build/native-unit-portraits/new-unit
```

它在已初始化的原生详情实体上调用 `wait_01` / `choice_01`，在 Present 前读取真实 backbuffer，按模型视口裁剪 PNG，
并记录来源帧和输入哈希。导出后检查姿势、裁剪边界和武器挂点，再上传到 Manager 的图片通道。

**不购买地查看收藏扭蛋**：在测试组件中启用 `CollectionPreviewOnly=1`，使用 `--pages-only`，不加 `--collection-draw`。
它只追加 `pages.collection.preview`，打开真实活动机台、价格和原生确认框，确认没有提交购买请求。
活动和收藏机台页只显示一张机台海报，不列出奖池中每台机体的头像。

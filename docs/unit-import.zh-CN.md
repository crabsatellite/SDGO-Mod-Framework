# 机体导入助手与 unit_catalog

这是 SDGO Mod Manager 的服主内容面板和可选客户端 Mod，功能 ID 为 `unit-import`，归类为玩法扩展。
打开面板不会修改游戏资源或停止现有服务。通用发布包只提供工具，不预装作者机体；
用户自己的机体草稿、图片、发布物与安装收据保存在本机工作区，不进入工具发行包。

任何来源按协议做好的包均可提交导入；是否可用取决于协议校验和当前支持的运行能力。来源拆包和来源格式转换不属于公开框架。

## 打开界面

打开 `SDGO Mod Manager.exe`，选择左侧「机体导入」，设置配套客户端、制作工作区和 WorldServer INI。
可以选择已有的 `unit-families.json` 所在目录，保留原草稿、编号、发布版本和历史。
留空工作区时使用 Manager 工作区下的 `data/units`。留空 INI 时仅作离线制作。
凭据只从本机 INI 读取，不出现在玩家包中。冻结版已带 Python、Pillow 和 pyodbc，RAR 解析需要本机 7-Zip。
源码调试使用同一个 Manager 入口：

```powershell
python -B tools/mod_manager.py --workspace D:/ModManager
```

开发信息视图可指定原生快照、单独构建的 `unit_catalog.dll` 或 7z 路径。
缺少组件时仍可检查和编辑草稿，确认发布会明确列为关键缺项。界面使用 Manager 的会话、版本检查和单一服务；
不再提供机体专属网页服务、启动脚本或关闭 Manager 的模块接口。退出 Manager 释放本模块工作区锁。

## 导入、补齐和确认

1. 选择或拖入 RAR/ZIP。读取 BIN 内部编号和字段，不根据文件名决定机体身份。
   未支持的布局、损坏记录、重复身份、不完整变形关系、缺少核心模型等情况会拒收，不能留下一个假成功草稿。
2. 单形态、变形目标为零时自动标为“无变形”。双形态分别展示其属性、目标、武器和资源；选择进入机库的根形态。
3. 已解析的属性直接展示。缺少的服务端字段保持为空，不默认为零，可手填、上传 JSON 定义，或明确选择原版模板补齐缺项。
   模板只补空项，不覆盖已从包中读取的数据。每个字段显示来源，补齐后仍可修改。
4. 选择原生永久机体物品模板。工具在受管范围内分配类别号，只登记机体类别，不创建商城 SKU 或添加扭蛋槽。
5. 检查依赖列表。可单独补传 BIN、模型、动作、特效、贴图和 SPR；缺少的武器必须同时有客户端记录和服务端定义。
6. 分别选择或上传商城、扭蛋图片，查看共用生成器的输出。商品预览使用普通商城实际读取的 122×122 已持有图鉴图标；
   生成器保留原生二维详情图、另一列表图片及候选头像的独立通道，
   默认沿用各位置引用的原生图片；选择「由所选源图生成」可替换对应通道并按实际画布生成。
   固定扭蛋直接调用已有 `Assets.card` 的头像裁切、原生卡框、等级条与稀有剪影生成逻辑，预览与机台编译共用。
   SR 等自定义扭蛋使用机体的独立候选头像，等级边框由游戏现有候选控件按等级绘制，不伪造 A/B/C 固定卡框。
   生成资源缩略图不是游戏截图，不能作为实际 UI 的验收。
7. 保存草稿，核对两张已加载的生成图标，逐项勾选后点击「确认图标并导入」。
   确认记录绑定当前内容版本及生成图片哈希，不冒充游戏内验收。
8. 需要试看实际游戏时，可选「准备独立预览副本」「打开原生预览客户端」，正常登录后查看候选机体。
   原生显示调用回执单独记录；调用回执、截图、实际出机与完整战斗是不同的验证范围。

若包中没有自己的图标，借用的原版图片可能属于其他机体。可用真实模型的原生准备／选择动作截图，
再上传 PNG；上传图片会切换为「由所选源图生成」。卡框、等级条和不同消费者的画布仍使用既有生成器。
机体一览会为每个机库根形态登记独立的原生目录条目，并生成 122×122 的正常／未持有图标；
变形态不作为第二台独立机库机体登记。没有配套设计图时不会借用模板机体的配方。

原生预览使用本模块管理的独立客户端副本，沿用原客户端的基础修复与连接配置，不停止原游戏、服务器或另一条测试线。
候选机体先只登记到这个副本的内存目录，复用游戏的商城机体渲染方法及 `UnitRadio → unitview` 路径。
商城此时还没有真正上架的 SKU，因此只显示原生机体视图，不把模板商品的名称、价格当成新商品展示。
购买、赠送与各类扭蛋提交请求在该预览副本中被拦截。准备预览不会写游戏服务端或发放机体。
预览副本保存在工作区 `native-previews`，应使用正常的“玩家客户端包”分发，不分发整个预览客户端。
面板提供清理过期预览副本的入口；只移除本模块创建、已过期且没有运行的副本，保留当前预览与草稿。

主包最多 32 MiB、解包总量最多 128 MiB、512 个文件；PNG 最多 8 MiB、边长 1–2048。
路径越界、链接、重复路径及包内安装程序/数据库脚本不会作为内容运行。
新机体 ID 与原生或其他受管机体冲突会阻止确认，本版不做不透明的二进制全文换号。
本版支持复用宿主已登记的技能，不凭新编号生成技能行为。缺失技能默认阻止确认；
对已验证可同步编码的技能 1/2，界面逐个提供「移除缺失技能 … 后导入」选项。
明确确认后，会将所有引用该技能的形态在客户端与服务端同时清为 `0`，记录主动移除的来源与警告，
保留原始 RAR/BIN，并使旧原生预览确认失效。其他技能、武器与变形关系不会因该操作改变。
原技能效果将不可用；这不是补齐或实现了原技能。技能 3 尚无已验证的客户端对应字段，不提供猜测性移除。
本版支持单形态或完整、显式的双形态关系；更多形态及新技能行为需要额外的已验证适配器。

### 服务端内部名与中文展示名

原生服务器部分定义列是 `varchar`，非中文排序规则下不能可靠存储中文。
这些内部名要求 ASCII；可读取包中的英文名或由服主填写/选择模板。
中文展示名独立保存到客户端宽字符记录与 `tbl_UnitNames.NameCN`，不会因此变成问号。
应用时逐字段读回核对，遇到截断、有损编码或外部修改则整笔回滚。

## 确认究竟写到哪里

- **配置了宿主 INI**：确认后用一个有应用锁的 SQL 事务更新机体、武器、名称和物品类别定义。
  仍保留原生服务器的缓存读取流程，工具提示需要正常刷新相应缓存，不自行重启 World/Store/Battle/Agent。
- **离线模式**：只登记到本助手的机体目录，生成玩家客户端包和服务端计划；界面明确显示“未写游戏服务端”。

两种模式都先生成并检查发布物，再提交确认状态。SQL 失败不会把草稿变成已导入。
服务端已提交而本地目录尚未完成保存时，发布事务收据用于启动恢复。
发布包包含同工作区所有已登记的运行记录，避免新增第二台时覆盖掉第一台。

只访问非玩家定义表、本模块所有权账本及已启用收集扭蛋的机体族元数据。不修改玩家余额/机库，不执行送机体过程，不替换原生 SQL 过程，
不设置商城价格或扭蛋概率。已启用收集扭蛋时，在同一事务登记初始形态及变形关系，供既有实时奖池读取。

## 分发、商城和扭蛋

已确认后可以下载“玩家客户端包”和单独的“服务端计划”。客户端包包含可信的配套 DLL、原生记录、受管资源、
公开定义、展示登记、符号片段和安装器，不包含服务器密码、玩家数据、日志或整套游戏文件。
它是部署包，不能重新当成原始 RAR 制作源导入。

玩家关闭游戏后，在 Manager「游戏功能」选择客户端并「导入客户端配置包」。Manager 调用内置可信安装器，
不执行 ZIP 自带的安装脚本；机体资源、目录和安装收据作为同一套内容安装。仍支持离线命令行安装：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Install-UnitCatalog.ps1 -ClientRoot D:/Game
```

安装器只更新本模块和清单中自己拥有的资源，保留其他 Mod 与全局开关；外部改动或冲突拒绝覆盖。
撤销安装也先关闭该客户端：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File Install-UnitCatalog.ps1 -ClientRoot D:/Game -Uninstall
```

**确认导入后不会自动送机体、创建商城 SKU、定价或插入扭蛋槽位。**机体的实际获取方式由服主配置：

- 商城：同一数据库的「商城商品」面板点「刷新物品目录」，选择新增机体物品，新增商品、设售价并应用。
  面板可显示已确认的商城头像。仅保存商品草稿还不等于已上架。
- 扭蛋：在「机体导入」点「同步已确认机体与扭蛋头像」，将定义与已批准图片登记到当前扭蛋目录。
  然后在「扭蛋机」选择对应机台、槽位和概率，再编译并应用。同步本身不改现有机台、价格或概率。
  已确认的 C/B/A 导入机体可进入原生自定义普通槽位；稀有槽仍遵守机台等级规则，S 级候选继续遵守 SR / SS 规则。

同步只接受已经应用到相同游戏数据库的发布；依据 `[DB Game]` 的服务器与库名指纹检查，
WorldServer / StoreServer 的不同 INI 指向同一数据库时可匹配，凭据不参与公开登记。
离线发布、未确认草稿、其他数据库、外来编号和过期目录版本都会被拒绝。
编辑已发布机体时，下游继续引用上一份已批准内容；重新确认后才切换新图片。
固定机台的卡面使用既有生成器生成 183×107 输出，再按原流程放入 256×128 纹理并使用准确子 UV。
自定义候选使用独立的机体头像和原生等级框，不能用固定卡面或同一张商城大图替代。
两个生成器的输出被相应消费者直接使用，无需手写 SPR 路径。卡面编译版本为 9，保留 master 的 PNG 取景覆盖与活动资源保留逻辑；旧版生成缓存需重新编译。
机体包自动包含供原生游戏读取的模型、动作、纹理与特效归档；工具同时保留本地资源副本。只复制松散文件不代表游戏可以读取。机体目录与扭蛋目录可同时启用；若已有旧版扭蛋目录，先更新框架再安装机体包。

玩家需同时安装配套机体包与更新后的机台资源。同步不会主动回收旧机台的选择。

`registrations.json` 以及 Manager 的 `/api/providers/units/api/units/registrations` 提供稳定 `unit:<root ID>`、
类别、名称、形态和同版的 `shop_sprite` / `capsule_sprite`。胶囊机台卡面是独立资源，不冒充机体的三张 UI SPR 字段。

停用会保留定义、编号与资源，不删除玩家已经持有的机体。彻底清除服务端定义属于另外的引用迁移操作。
已发布的机库根形态保持固定，避免一次编辑改变玩家已持有机体的身份。
请备份服主工作区，保留草稿、稳定 family 身份、编号和发布收据；不要用空工作区重新分配已发布内容。

## 构建和验证

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A Win32 -DBUILD_TESTING=ON
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure -R "unit_(catalog|import)"
```

原生客户端支持 `GOnline-54BE1568-00C97000`，使用精确 EXE 哈希和签名校验。
在最后一张原生表加载后以原生分配器注册完整 unit/weapon/item 记录，同时检查数据树中的跨类型编号冲突。
运行时先完整预检和分配；若已经写入部分记录后原生发布意外失败，会记录诊断并仅终止本次客户端，
避免半组机体进入游戏。这是失败后停止，不是原生数据树事务回滚，也没有新增跨端版本握手。
原生核心数据、模型/动作/挂点、直接资源依赖与真实游戏行为的验证层次不同。
实际出击、各武器/技能/必杀、变形触发与返回、多客户端同步、复活、经验和能源仍需相应原生 GameTest 和游戏内验收。

输入协议与历史调查依据保留在源码仓库的 `docs/unit-import-protocol.zh-CN.md`，不作为发行包的默认机体配置。

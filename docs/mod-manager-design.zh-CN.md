# 统一 Mod Manager 设计

## 产品入口

管理功能只提供 `SDGO Mod Manager.exe` 一个入口。它启动同一个本机界面和管理服务；不再为每个 Mod 提供独立 EXE、启动脚本、端口或网页。Mod 游戏运行库不依赖 Manager 常驻；确实需要后台工作的模块以内部服务登记。

玩家在游戏中使用的操作接入相关原生页面：机库整理、重复机体兑换放在「机体管理」页，保留预览、确认和服务器回执，不另开桌面窗口、不挂全局悬浮工具栏、不要求记快捷键。Manager 负责安装、配置、管理接口与 Mod 后台任务；普通玩家不应离开游戏完成这些游玩操作。其他游戏操作也应整合到对应的原生页面，保持一致的使用方式。

首次启动默认是日常管理：普通玩家和服主都可选择客户端/服务器，添加 Mod、管理商城/副官/扭蛋机、设置奖励和联机、导入或分发配置包。管理服务器属于正常用户能力，不作为开发权限隐藏。

只有内部代号、原始字段名、Hook 符号和诊断开关放进开发信息视图。相关开发接口会检查当前模式；收起开发信息不影响日常管理能力。自动 Bug 修复不占据日常功能列表，只在修复归档查看。新账号默认内容虽然原分类属于 fixes，但它是服主日常配置，仍显示在功能列表。

每个功能提供“复制给 AI 配置/调试”和“发现 Bug，复制给 AI 报告”。说明包含原理、组件/配置位置、地址、可调点、版本和兼容性与已知限制；报 Bug 的文本指向统一 GitHub 仓库，要求 AI 先查重复 issue，再根据真实复现创建报告。生成说明不会自动发 issue，也不读取或复制密码、令牌和原生数据库凭据。Issue 用说明不附带本机绝对路径或端点。

## Mod 注册契约

程序发布分官方基线与明确允许分发的本服补丁，内容层另行保存机体、素材与共享参数。玩家入口只引用一份整合配置，锁定各层版本并原子安装；镜像只改变传输位置。维护者目录保留开发预览，玩家目录才自动跟随发布。范围、清单与操作见[本服程序包](owner-programmes.zh-CN.md)。

每个 Mod 附带 `manager.json`，声明版本、标题、分类、适用宿主、玩家说明、配置字段及动作。字段声明类型、默认值、范围、存储文件/节/键、可见模式和生效方式。动态内容模块通过标准 Provider 返回集合、编辑字段、动作和状态；不提供另一个 Web 服务，也不将任意脚本路径作为浏览器可执行命令。

同一个 ID 的客户端/服务端组件共享功能页，配置始终绑定一个明确宿主，不能误把客户端配置写到服务端。未认识的第三方 Mod 可以显示安装信息和自身启用开关；详细配置需要它提供注册文件，不能猜测并改写未知字段。

## 统一能力

### 依赖与数据维护契约

`manager.json` 使用 `dependencies.required`、`optional`、`conflicts` 声明关系，支持最低模块版本、条件与宿主范围。
`provides` 声明具名接口版本；接口版本按精确值匹配。可选接口允许提供者缺席，同时启用时仍须兼容；循环关系拒绝加载。
构建工具从同一注册文件生成原生 INI 契约，符号地址的 `requires` 保持独立含义。

配置与安装共用跨进程目标锁。数据影响确认绑定操作、参数、目标与当前修订，只能使用一次。
固定目录写入在数据库提交期间持有原生程序映像屏障，防止服务在维护中重新启动。
提交回执区分待重启、已生效、失败和需要恢复；已提交的数据不会因后续文件错误被谎报为回滚。
已知内容的退役保护也适用于旧清单，升级不改写既有历史。退役历史先留本地备份，再执行显式模块迁移。

运行回执使用 PID、进程创建时间和配置文件摘要核对。可选 API `ConfigurationRevision`／`ConfigurationApplied`
让热重载组件确认稳定读入的配置；未收到确认时保留待核实状态。固定目录还需新的业务监听及本次原生表加载证明。

完整客户端来源固定发布者与不可变 Git 提交，传输读取原始对象字节，避免签出或归档转换换行。
大归档逐段验证后再核对整体摘要。程序换名期间旧、新映像均受写句柄保护，恢复清单与运行文件属于同一事务。
用户配置、仅本地根目录和未声明退役的自定义文件独立保留；原版程序和私人分发来源不进入框架公开 Release。

- **配置**：表单生成、字段校验、原文件注释/编码保留、版本指纹、原子保存、只修改登记的键。区分已保存、需要重启、实际运行确认。
- **集合**：商城商品、副官、扭蛋机统一在框架内列出、搜索、新增、编辑、删除、恢复和导出。原有业务校验由 Provider 复用；删除数据与删除旧 UI 入口是两件事。
- **动作**：声明参数和结果，统一处理加载、错误、产物下载与执行进度。配置包只包含明确允许的客户端文件，不包含服务端凭据、数据库快照或管理器本机路径。
- **状态**：分别展示配置、运行心跳和服务器响应，区分已保存配置与实际执行结果。
- **工作区**：选择客户端和服务端路径后保存到服主本地配置；通用源码/分发包无作者电脑路径。数据保留原路径或通过显式迁移复制后校验，不重置既有商品、副官、扭蛋机和钱包队列。

## 界面与 UI 库

界面使用 `manager/static/ui.css` 与 `ui.js`（SDGO Mecha UI）：机库夜色底、RX 三色加光束青、切角装甲板、HUD 角标和警示条。组件、令牌和用法在开发信息视图的「UI 组件库」（`/ui-kit.html`）里浏览。新页面直接使用 `.ui-*` 类；放进 `.ui-auto` 容器的普通按钮、输入框、表格会自动套用同一外观，`.ui-plain` 可退出。Shadow DOM 面板通过继承的 `--ui-*` 令牌取色。

机体插画、机库和装甲纹理不进仓库也不进发行包：`/api/art/<key>` 在运行时从已登记客户端的 GPackData 读取白名单纹理并裁切。没有客户端或纹理缺失时请求返回 404，界面保留自绘外观。

## 已统一的入口

Manager 取代了原先的奖励网页、FRP 配置生成、AI 清单工具、商城 EXE、副官和扭蛋机网页入口；这些旧入口不再使用。
真实配置、原生游戏 EXE、Mod DLL、账号和恢复备份不属于旧入口，迁移时保留。

## 验证要求

检查所有随包 Mod 都有注册；日常管理能操作客户端和服务器，自动修复只进归档，开发诊断信息按视图隔离；AI 说明和 Bug 报告不泄露凭据；保存不损坏未登记键；并发更改会拒绝覆盖；跨目录、ZIP 路径和任意命令不可通过输入注入；集合 CRUD、编译/导出与已有业务输出一致；分发包可在空白目录启动，只有一个用户入口，不依赖旧 UI 文件。

双源完整更新将框架运行 ZIP 与服主内容 Git 树合成为一份有效文件清单；程序路径属于框架，声明的配置覆盖与生成素材属于服主，个人配置单独保留。两层在写入之前完成兼容性检查，使用同一恢复日志和目标锁；回执分别记录两层提交与框架版本。运行程序版本与磁盘已安装文件分别报告，待重启不等于已加载新版本。

通用内容模型是原版基础客户端＋官方 Mod 版本锁＋服主配置档。Git 是传输适配器，不是配置的定义；HTTPS 文件/包和离线目录复用同一组合与提交逻辑。完整客户端仓库是部署层的可选快照。SQL 归属由 distribution/artifact-ownership.json 与内容边界指南声明，玩家导入不执行 SQL；私有源也不应包含密码、生日名单或玩家库存数据库。

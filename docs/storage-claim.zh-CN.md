# 保管库一键领取

[English](storage-claim.md) · [返回功能目录](../README.zh-CN.md)

客户端 Mod `storage_claim` 在保管库两个页签的右侧添加「一键领取」。使用当前客户端原生皮肤、文字和点击事件，玩家不用补素材、填账号或启动 Manager 后台。

## 使用

1. 进入保管库，选择要领取的物品或礼物页签。
2. 点击「一键领取」，再点击「确认领取」。整个批次只确认一次；领取限时物品可能开始计算使用时间。
3. 一次领取当前页签全部分页：先读完所有分页，再把全部奖品连续提交服务器，最后刷新一次列表。底部显示进度与结果，领取中按钮变为「停止领取」。

读完列表后，每件奖品的原生预检和领取请求一笔接一笔连续发出：收到回应立即发下一笔，中间不再刷新列表、不再等待间隔，几十件奖品通常几秒内完成。
使用完整实例 ID；相同物品的不同奖品记录分别领取，不按名称或格号猜测。礼物保留原信件，已领取的信件自动跳过。

服务器拒绝的奖品（例如机库容量不足）跳过并计数，其余照常领取；需要选择内容的礼包留给原生按钮单独处理，本 Mod 不代选。
完成后显示“已领取 N 项”，有跳过时一并说明数量和服务器错误码，不逐件弹出原生失败窗口。
断线、超时或离开页面时停止；停止只阻止后续请求，已经发出的领取以服务器最终结果为准。
结果未确认期间不重新发起批次，不自动重发领取请求；请等待回应，必要时重新登录核对。
领取期间保留关闭按钮，暂时拦截原生行操作、分页和页签切换，避免与批次交叉。

## 安装与设置

玩家通过服主提供的客户端包或更新获得。完整框架包包含该玩法扩展，Base 包不包含；也可关闭目标客户端，在 Manager 中导入专用增量包，再正常启动游戏。
只需客户端部分，不需要服务器 Mod、SQL 权限、HTTP 服务或专用启动器。
支持 `GOnline-54BE1568-00C97000`；代码地址、原生布局或皮肤不匹配时不显示新增入口，保留原有领取方式。

Manager 可停用本功能。开发模式提供 `ReplyTimeoutMs=10000`、`MaxClaims=5000`；正常使用不必调整。
原生分页最多 255 页：物品超过这个范围时，领取完前面部分后自动再读一轮；礼物信件超过时停止提示，不会页码溢出。达到单批上限可以重新发起批次。

## 开发者说明

原生 `1396.uir` 为 450×540，页签在 y=64；新增按钮在 x=291、y=64，状态行在 y=520，不覆盖原列表、分页、过期提示或关闭按钮。
页面接入和收到点击分别写入日志，便于区分“已加载”和“已实际交互”。
普通物品与礼物复用原生服务器预检和发放协议。每笔预检和领取都是一次独立的存储过程，不依赖前一笔预检的会话状态，因此可以连续提交。
World 用多个线程处理请求，同一账号的请求重叠时会拒绝后到的那笔，因此始终只有一笔请求在等待回应。
成功回执按奖品 ID 匹配；错误回执不带 ID，归属唯一未回应的请求。超时按“多久没有收到任何回应”计算。
Mod 自己发出的列表请求同样把页面标记为加载中；原生到账处理器自行重读列表时，最后的刷新会等它完成。
取消后迟到的预检回执由 Mod 消费，不交给原生自动领取分支。领取成功仍交原生处理器发放和刷新库存，Mod 不写数据库。

自动测试使用合成客户端缓存、物品列表、网络回执和原生 UI 接口替身，覆盖整页签读取、逐笔连续提交、乱序回应、容量拒绝计数、手动选择、预检/领取中途停止、超时、断线、迟到回包、分页范围和初始化失败。
原生 GameTest 的 `storage_gift` 页面组在真实客户端和服务端上执行一次确认领取，核对收集数、到账数、跳过数和领取后剩余数量。

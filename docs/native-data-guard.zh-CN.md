# 原生数据与生命周期崩溃修复

[English](native-data-guard.md) · [返回功能目录](../README.zh-CN.md)

## 作用

修复机体数据缺失、或机体管理页等待数据时的客户端闪退，并让闪退日志记录正确的现场。客户端 Mod `native_data_guard` 处理以下情况：

- 浮游炮挂点名称只接受 1–6 号索引。其他索引返回游戏原有的空结果，避免越过名称数组。
- 两种原生名称显示格式遇到缺失记录时显示“未命名”。已有名称继续使用原生记录。
- 机体基础信息记录尚不可用时，只跳过本次详情刷新，避免普通或变形详情继续读取空记录。记录就绪后的原生选择或刷新回调继续使用原有显示流程。
- 机体信息刷新遇到缺失派生记录时沿用游戏已有的分母为零分支，保留默认百分比，避免读取空指针。
- 模型缺少可选变形数据时，基础模型继续完成原生载入和状态设置。
- 原生异常报告使用独立的栈回溯上下文；报告中的异常地址、访问类型、模块范围和寄存器来自回溯前的原始现场。
- 机体管理等待库存数据时，服务保存一份自己的原生消息副本，而不是持有消息分发器的临时对象。
- 模型材质查询先核对原生容器的实际边界。可选贴图槽没有对应材质时继续下一槽，保留原生模型提交和收尾。这条共用查询覆盖机体一览、扭蛋预览等原生页面使用的机体展示。
- 房间相机只接受原生的 0–29 号样本。拖动或滑块产生非法下标时保留原选择；模型未就绪或相机状态无效时跳过本帧更新，后续就绪帧继续原生更新。
- 登录后的初始库存尚在请求容量或分页接收时，暂存页面打开意图，先让当前原生收包处理器完成工作。机体一览的独立请求也等待同一原生完成标志，然后自动打开；切到其他页面或更换会话后取消过期请求。等待时间取决于实际收包完成，不使用固定秒数。

这些保护不会补齐缺失模型、添加机体、更改武器或调整战斗奖励。保护范围是上述数据路径；其他位置的客户端异常需要单独定位。

## 使用

安装服主提供的客户端包或更新。Mod 在支持的客户端上自动启用，在 SDGO Mod Manager 的「修复归档」中可以查看；没有需要玩家调整的参数。安装或更新后重新启动客户端。

支持的客户端标识为 `GOnline-54BE1568-00C97000`。框架在启用前检查命名符号的原生指令。其他客户端版本或同一位置存在冲突补丁时，需要先核对兼容性。

## 日志

启用成功时，框架日志记录 `native data guards active`。缺失名称、信息记录和可选变形记录会输出有限警告；正常数据不会逐帧输出警告。发生原生异常时，框架日志会额外记录回溯前的原始寄存器和访问地址。

`base information unavailable` 表示本次基础信息刷新被安全跳过，并附机体 ID。加载完成后可重新选择机体或打开机体管理；若持续出现，服主需要检查该机体的客户端资源，保护逻辑不会生成缺失内容。

再次闪退时，保留当次原生异常日志、当前框架日志和上一份框架日志，再重新启动。核对会话和时间；复制来的客户端文件夹可能带有其他安装的历史异常记录。

`wait-room camera sample` 表示相机下标被拒绝；`wait-room camera data is not ready` 表示本次更新等待后续帧。两类警告都有次数限制。缺失材质槽由开发者观察器计数，不逐次刷日志。

## 开发者说明

原生浮游炮索引条件使用了“或”，使任意有符号索引都能进入数组读取。经过指令校验的两字节分支修正，让非法索引进入游戏已有的空结果分支。

名称保护只作用于两个已核对返回地址的显示调用者。静默预检查使用原生的 type-2/type-24 名称键计算；记录缺失时返回不可变的文本记录，文字位于第 13 字节。其他调用者及有效记录保留原生查询行为。

模型保护位于基础模型载入之后的可选变形记录读取处。记录为空时保留 x86 原生上下文，继续原有收尾流程；不会跳过整个加载任务，也不会把机体替换成另一台。

信息页保护位于派生记录返回后的第一个读取处。记录为空时只为被移位的原生读取提供一个零值记录，使后续代码进入游戏原有的默认百分比分支；有效记录和计算公式不变。

整个详情入口另行使用原生静默查询，预检查接收器 `+0x114` 的基础 type-2 记录。原版查询失败后仍保留空记录，变形模式读取其 `+0x13C`，或把它传给后续详情读取器。预检查失败时不改写接收器、不调用这些读取器；成功时仅委托原函数一次，不锁定失败状态，后续回调仍可正常刷新。原生二级变形查询及其基础记录回退保持原样。

机体管理生命周期保护只作用于已核对的延迟消息槽。消息分发回调返回前先调用原生复制虚函数；服务复制时深拷贝这条自有消息；重复请求或服务销毁时释放仍挂起的副本。原版加载完成路径继续把消息复制进队列，并销毁服务持有的副本。

异常报告保护包装原生异常记录器，并只在该线程、该次记录期间把 `DBGHELP!StackWalk` 的可写 `ContextRecord` 指向独立副本。原生记录器继续执行原有的栈回溯和报告流程，但回溯不能再改写随后打印的寄存器。

`native_data_guard_actual_dll` 执行实际构建的 DLL 和站点跳板，并覆盖延迟消息保存、替换、服务复制、正常完成和销毁。安装本 Mod 后，原生 GameTest 的 bootstrap 还会调用宿主的挂点、名称格式和信息刷新函数，再继续认证、建房及战斗流程；信息刷新使用私有展示接收器核对原生默认百分比，不改写活机体或数据表。重复请求、服务复制和销毁对延迟消息各有明确的所有权；原版完成路径仍只入队一个副本，并释放服务持有的副本一次。`SdgoNativeDataGuardGetStatusV1` 和 `V2` 保持原有观察器 ABI；`SdgoNativeDataGuardGetStatusV3` 追加原生延迟消息复制、替换、复制失败、原生完成次数和当前仍由服务持有的消息数。

实际 DLL 测试还覆盖两种详情模式的基础记录缺失、数据表不可用、空查询结果、页面状态不变，以及后续有效回调恢复刷新。原生 bootstrap 以私有接收器和不存在的键调用两种模式的真实完整详情入口。`SdgoNativeDataGuardGetStatusV4` 追加跳过基础信息刷新的计数，同时保留早期导出。

材质保护核对原生 CModel 的两组向量字段。有效查询及另行使用资源表的共享材质分支仍只调用一次原函数。贴图结果站点仅跳过没有材质的当前槽，继续原来的循环递增和收尾，不伪造材质或更换素材编号。`native_material_guard_actual_dll` 执行实际构建 DLL 的查询和 x86 结果跳板，覆盖空、短、异常及有效容器。

房间相机使用 30 个样本。选择写入和逐帧更新都校验下标范围，不写回非法值，也不擅自改选另一个样本；原生相机模型存在后才更新。这条共用更新由原生房间主状态调用，不局限于某一个菜单按钮。

`SdgoNativeDataGuardGetStatusV5` 在保留 V1–V4 的基础上，追加不可用材质、跳过贴图槽、拒绝相机下标及跳过相机帧的计数。原生 bootstrap 用私有材质、选择和未加载房间接收器调用真实挂钩入口，不修改活机体、真实相机选择或数据表。

初始库存保护读取 `CUnitInfo+0x20` 的原生完成标志。保护位于底部菜单业务和机体一览的独立入口，先于导航命令和网络请求，避免初始收包服务被提前替换。MyRoom 的原生库存初始化入口继续放行；不合并库存请求、不伪造回包、不忽略 `0x279A` 或其他服务端错误。场景切换与音乐等已有钩子保持各自所有权。

菜单请求只保留应用、库存归属、源页面及动作编号。原生普通帧完成更新和验证后，重新查找当前已登记的菜单及控件，再通过原始菜单回调恢复动作，保留父控件和 starter-busy 检查。菜单重建、暂时不可见或忙碌时继续等待；更换应用、库存或页面后取消过期意图。机体一览在同一完成边界打开一次，不保存临时消息或控件指针。

`SdgoNativeDataGuardGetStatusV6` 追加等待、恢复及一览请求取消计数，同时保留早期观察器导出。实际 DLL 测试覆盖容量请求阶段、分页阶段、MyRoom 初始化放行、忙碌回调、菜单重建及页面／归属更换。原生 GameTest 的 `early_navigation_before_inventory` 场景另行核对真实分页末包、完成标志、保护触发、页面就绪和正常返回。

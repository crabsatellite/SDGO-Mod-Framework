# 原生 GameTest

[English](game-test.md) · [返回功能目录](../README.zh-CN.md)

开发用可选 Mod，默认关闭。测试在真实客户端进程内执行，通过正常业务请求
与真实服务端通信。外部运行器负责准备独立客户端、启动和收集结果，不操作桌面。

每个场景按“发起请求 → 等待真实回包 → 断言状态”执行。登录、服务器数据、
建房和战斗加载均走正常游戏流程，不伪造机库、房间、机体记录或服务端回包。

测试账号与注册重试规则保存在本地私有配置中。缺少步骤、断言失败、未处理的原生异常
和超时都会判为失败，结果输出为 JSON 和 JUnit XML。仅安装 Mod 不会自动运行测试。

测试使用本地已有的原生测试环境：独立的客户端副本、原生服务端和原生 SQL 数据库，与正式服完全隔离，不用 Docker。
并发冲突时复制测试环境并配置独立端口和原生 SQL，完成后删除整个任务副本。
普通测试绑定已有账号与机体；测试程序和数据库副本只留在本地。

## 无需登录的 FPS 参数验证

构建 `game_test_client`、`fps_limit`、`sdgo_core`、`d3d9_shim` 和 `sdgo_data` 后，
以正常客户端为只读模板运行矩阵：

```powershell
python tools/game_test_fps.py --client-template D:\Games\SDGO --stage build/stage/Release --work-dir build/fps-runs --results-dir build/fps-results
```

矩阵使用同一个 GameTest 后台桌面、真实 D3D9 设备、静音 Miles 驱动和回环网络策略，
停在原生登录页，不读取账号配置，并清空测试副本的已保存登录资料。
依次对照「禁用 Mod、配置 160」与启用后的 30、60、120、160。
原生登录页仍需要连接兼容的真实后端；可通过 `--target-host`、`--login-port`
选择已有本地测试入口，不会因此创建账号或提交凭据。
整轮默认超时为 600 秒，为原生资源加载预留时间，可用 `--timeout` 调整；
这不改变频率断言或采样窗口。
后台进程使用与普通游戏相同的 Windows 正常优先级；宿主 CPU 满载时，低于正常优先级会使
原生加载及计时采样长期得不到调度。后台桌面与静音隔离继续生效。

每轮读取真实应用的 FPS 字段及已初始化的计时器间隔，再以独立的 QueryPerformanceCounter
测量原生更新和成功 D3D9 Present 的频率，连续采样三段，每段三秒，保留全部窗口及平均值。
逻辑更新须保持原生 60 Hz 的 80–110%，不随渲染上限提高；成功 Present 须有正值，平均不超过启用上限的 110%。
最小提交间隔须符合实际限速周期，允许 0.5 毫秒与周期 10% 两者较大的调度误差。
正式 Mod 的观察接口独立确认逻辑/渲染目标与实际周期；30 FPS 对照须真正触发等待。
禁用对照不检查渲染上限。渲染低于上限时照实记录，不承诺达到该吞吐量。
断言和结果沿用 GameTest 的 JSON/JUnit；该场景验证登录页原生渲染，战斗计时和画质另行测试。

运行器先导出报告、原生事件及后台环境回执，再核对本次运行的进程已退出并删除所属客户端副本。
模板和其他测试保留；换环境复测时指定新的工作及结果目录即可。
单独验证一档也可使用 `game_test.py prepare --fps-cap 160` 后执行通常的 `run`；
添加 `--fps-mod-disabled` 可取得原生强制 60 的对照。

完整原生对战回归可在常规已有账号的准备命令中加入 `prepare --fps-gameplay-cap 160`。
运行前会封存渲染上限与观察器配置。实际 AI 移动后，场景核对 60 Hz 逻辑更新；
选择高于 60 的上限时，渲染还必须实测超过 60 FPS，之后继续正常对战、结算和返回流程。

### 复用本地原生后端

`tools/game_test_backend.py serve` 运行已经配置的本地测试服务端，复用其独立原生 SQL 实例，
不使用 Docker，也不在每次重试时复制或还原数据库。后端的 `backend.json`、`private.json`
和实际 SQL 文件必须绑定同一测试副本；启动前会核对存活的 SQL 进程及数据文件路径。

server stage 须构建 `winmm_shim`、`sdgo_core`、`sdgo_data`、`pvp_ai` 和 `game_test_server`。
以下示例假设测试副本已经使用 `127.93.0.1`，私有数据库配置也已就绪：

```powershell
python tools/game_test.py prepare --client-template D:\SDGO-Test\client --stage build/stage/Release --run-dir build/fps-probe --target-host 127.93.0.1 --login-port 5001 --fps-cap 160
python tools/game_test_backend.py serve --work D:\SDGO-Test\server --client-run build/fps-probe --stage build/stage/Release --startup-xml D:\SDGO-Test\server\ServerStartUp\ServerStartUp.xml --lifetime 1800
```

启动集合同时读取原生启动 XML 和频道表；等待本次启动各 Battle 的
`Table Download OK.. Time Procedure Ready..` 及 `backend_ready` 后再运行客户端。
TCP 端口开放不能代替原生表加载完成。FPS 套件无需账号；其他套件绑定已有私有账号配置，
后端观察器另需 `serve --host-pilot-id <实际原生驾驶员 ID>`，工具不固定账号 ID。
只改客户端场景时可复用已就绪的服务会话；更新服务端候选 DLL 时才重启所属后端。

```powershell
python tools/game_test_backend.py stop --work D:\SDGO-Test\server
```

停止后核对所属服务进程已经退出。保留共享 test、原生 SQL、已有账号和公共资产；
测试通过后，成功测试的临时记录及所属并发副本移入回收站，失败诊断保留到问题解决。
测试副本、数据库和私有配置只留本地，不作为正式运行文件的发布来源。

测试默认使用独立后台桌面，副本中的 BGM、音效和语音全部静音。后台窗口与前台
归属有独立回执；不满足条件就失败。旧 D3D9 的设备在专用图形线程上创建，仅使用
不可见、不可激活的代理窗口；真实游戏页面仍留在后台桌面。禁止全屏，逐窗口验证代理身份和前台归属。
锁屏导致输入桌面访问被拒绝时，框架改为核对独立游戏桌面及 Default 桌面上唯一的隐藏图形代理，
并明确记录输入桌面状态不可读。其他读取错误、未识别窗口或前台归属异常仍会使测试失败。
原生 Miles 驱动使用 WaveOut，按驱动验证主音量为零。逻辑测试副本关闭原生
后处理效果，同时将各项原生特效等级设为零，并读取实际运行标志；该配置用于逻辑与协议测试，画质和后处理应在可见客户端中单独测试。
本机直连测试只绑定回环地址，不创建公网监听，
不修改系统防火墙或通知设置。非本机测试需要预先具备其专用防火墙规则的管理权限；
准备失败时不会弹出提权窗口或回退到交互运行。

受保护输入桌面拒绝读取时，FPS 与本机直连 PvP 测试可核验固定的 `WinSta0\Default`：
该桌面必须只有同一进程、身份一致且不可见、不可激活的图形代理，真实游戏窗口仍在独立桌面，
前台归属、静音和网络检查继续生效。回执保留实际输入桌面名称和状态为未知；
无法识别、可见的窗口或其他观察错误仍判失败。

默认复用 `%LOCALAPPDATA%\SDGO-GameTest\account.ini`，也可用 `--account-profile`
指定已有配置。普通重跑不会注册新账号；只有显式 `--create-test-account` 才允许
首次创建持久账号配置，且不会覆盖已有文件。

登录后的机库分页先在原场景完成，后续用例再进入机库。已有大量机体的账号同样等待原生
初始化标志和完整库存扫描，不会在分页中途提前切换场景。

新账号初始化包括昵称、新手测试退出、首次机体抽取和必要的游戏内确认。
这些步骤同样等待正常服务端结果，随后才运行对战场景。

开发者可通过 [`game_test.h`](../include/sdgo/game_test.h) 注册按帧执行的测试，
在原生主线程等待实际业务事件并进行断言。

构建后，用已有正常客户端作为模板。模板需要安装对战 AI，目标服务器需要启用
`pvp_ai`。运行器只启动独立客户端，不重启现有服务器。

```powershell
python tools/game_test.py prepare --client-template D:\Games\SDGO --stage build/stage/Release --run-dir build/gametest/pvp --mode-sequence 1,3,9
python tools/game_test.py run --run-dir build/gametest/pvp --timeout 3600
```

仅首次没有测试账号配置时，在 `prepare` 后加 `--create-test-account`；以后直接
复用同一配置。首次准备独立客户端，后续对同一 `run-dir` 添加 `--reuse-client`，
在确认进程已停止、文件完整后复用现有客户端，每轮生成新的运行 ID。
上一轮回执与二进制哈希集中保存，旧任务及重复文件进入回收站；不会再复制整套客户端。
被其他任务引用的只读归档基线不能作为复用目标。同一账号禁止并发运行。
需要换用另一个已有测试账号时，在 `--reuse-client` 后同时指定
`--rebind-existing-account --account-profile <已有账号配置>`。客户端必须已停止；目标配置须声明
`registered` 或 `existing_account`，且不使用注册重试。框架同时锁定旧、新账号配置，保留两份配置，
复用客户端文件；需要服务端回执时，观察器也须绑定目标账号的实际驾驶员 ID。
复用功能需要开发环境安装 `Send2Trash`，缺少时会停止，不会降级为永久删除。
进行枪械开火回归时，在测试副本的观察组件中启用 `BattlePlayerCombat`，并将
`BattlePlayerWeaponSlot` 设为普通远程武器槽（`0`–`2`）。程序发送原生换武器请求，等待实际绑定，
除输入、移动和攻击状态外，还要求观察到真实弹药消耗。默认 `-1` 保持当前武器；
测试不会强制改写武器数据、弹药、冷却或 FSM 状态。
同一开关也支持原生 SDK 协调会话中的各个角色。只有确认该角色绑定的房间、驾驶员、本轮战斗和
原生控制释放后才施加输入，结算后释放；默认仍关闭。

验证收藏扭蛋限额拒绝时，使用 pages-only 的 collection-draw 场景，并在测试观察组件中设置
`CollectionExpectedStatus=6006`。启动前明确准备隔离测试库中的已用尽限额；该轮要求真实购买被拒绝且
没有奖品，不算作成功抽取/领取。对比购买前后的原生钱包、限额和领取箱，确认退款；另以默认 `0`
完成一次成功抽取和领取。

对战人数回归可在 `prepare` 中组合 `--expected-ai 7 --ai-allies 0 --random-teams`，
请求原生随机真人分队，并验证房主对面恰有 7 个 AI、本方没有 AI。
省略 `--ai-allies` 时沿用原有的平衡测试布局；这两个参数只用于完整对战场景，不适用于页面或任务烟雾测试。
可同时加 `--random-loadout` 验证随机机体和该人数布局组合，所有参数写入封存任务。
`--same-room-rematch` 验证结算返回后真人仍为房主，并在同一房间完整再打一局，最后才离房；
此回归不与随机机体、页面或账号准备场景混用。服务端报告需要每个模式有两次完整战斗，不能用第一局结果代替第二局。
自动补位指令也可直接纳入原生回归：单人 8 人房使用
`--expected-ai 7 --ai-allies 3 --ai-policy fill` 验证 `!ai fill`，或
`--expected-ai 7 --ai-allies 0 --ai-policy enemy` 验证 `!ai enemy`。
`--ai-teams coop` 验证真人跟随房主同队；省略或写 `versus` 沿用原生手选／随机。
这些参数可与 `--random-teams`、`--random-loadout` 组合，敌友仍相对房主最终阵营；封存后的原生房名须在 20 字节内，过长组合应分场景测试。
普通 Grid/Tag 回归只读核对账号已选的战舰：1–4 台各不重复的已有机体、有效旗舰和不超过 10 的原生点数。
不要求先重建四机体编队；专门的 `--deck-only` 编辑场景仍使用显式四机体声明，走原生 Save/GoOut 回执。
连接地址默认 `127.0.0.1:5001`，可用 `--target-host` 和 `--login-port` 修改；
服务器和频道由原客户端正常流程自动选择。
默认 `--network-policy direct` 仅在测试副本关闭继承的地址转发，并在登录前核对
该进程实际建立的 TCP 连接。要专门测试服主的 FRP 路由，显式选择 `preserve`。

示例依次测试普通、死亡竞赛和队长模式。每种模式都经过
建房、真实开局、AI 状态断言和正常结束返回；也可指定单个模式排查。

普通对战的定向检查可用 `--ai-difficulty Hard --expected-ai 7` 封存原生难度指令；
再指定 `--ai-layout allied --expected-ai 6` 则检查五名 AI 队友与一名 AI 对手。
此队伍配置需新观察会话，复用会话的前缀会使指令超出原生房名上限。
`--ai-pool-level 1` 至 `5` 配合 `--expected-ai 1` 选择机体池，不能同时覆盖难度。
测试 Mod 的 `BattleAiBehavior=1` 要求实测必杀受击者恢复、移动射击和远距离追敌；
`BattleAiActivity=1` 单独检查每名预期 AI 是否取得目标并实际移动或攻击，面对可见敌人且控制空闲时
连续十秒保持中立不动会失败。默认关闭，可在 Manager 中测试 Mod 的开发设置里选择。
只读诊断记录逐台活动统计、武器／控制状态和采样间隔，不会移动机器人或伪造战果。

`BattleAiDeaths=1` 记录原生死亡身份，再加 `BattleAiTeleport=1` 则必须观察到本地 AI
真实瞬移、位置改变、血量保留且没有发送销毁请求。这些可选检查只观察原生战斗。
Grid（`6`）和 Tag（`7`）会通过原生业务切换 VS 频道，并要求账号已有完整战舰编队。
缺少编队或服务端拒绝会判为失败。
回执位于运行目录的 `receipts/report.json` 和 `receipts/junit.xml`。

准备账号时可单独使用 `--bootstrap-only`、`--battleship-only`、`--gift-requests-only`
或 `--deck-only`，这些场景不计为对战通过。领舰走原生教学；赠送走现有账号的
正常邮件业务，需目标服务器启用正常赠送服务并独立验证处理结果。编队从私有
账号配置的 `[deck] unit_uid0` 至 `unit_uid3` 读取四台实际持有的机体，等待原生
保存和出击舰回包。准备完成后重新登录同一账号运行对战，不补写机体或数据库记录。

使用 `--pages-only` 可验证真实登录后的机体管理页面、库存读取、两种兑换预览和
取消。测试逐台比较机体 UID、槽位及出击机体；存在兑换候选时不会提交兑换。
页面场景不计为对战通过。
观察组件 0.1.8 起可用 `--pages-only --page-group hangar` 封存仅机库的读取、预览和取消，
连同登录及可选的出击机体选择。该只读范围不执行保管库领取、购买或其他页面操作，不与商城、
收藏抽取范围混用；完整页面组的检查规则保持不变。
该场景还通过原生按钮打开保管库，等待消息循环和真实列表回包，验证确认领取流程；
空库通过只代表空库路径，不代表物品到账。扭蛋检查核对五张原生目录表，进入实际
扭蛋页面后检查 9301 的列表与确认数据源货币、以及收藏机的原生价格，不会购买。
该场景要求安装机库、保管库、操作员与 AI 目录、扭蛋目录和货币修复 Mod，
以及服务端 1200 格机库 Mod。
目录检查从真实原生表逐条读回配置的操作员与 NPC，核对名称、类别引用、NPC
字节和来源机体哈希；这些目录检查不代表商店交互或任务通关。

要覆盖商店页面，在 `--pages-only` 中同时传入 `--shop-assertions` 和
`--shop-display`。两份开发用断言文件只描述服主已有的现货，复制到测试副本后
按路径、SHA-256 和 revision 绑定。场景读取原生名称和永久／租赁选项，打开购买与
赠送预览后取消，并比较完整机库与钱包。它不会安装商品、购买或赠送。
查询先打开原生搜索页，再点击该页的 `FilterBtn` 并等待原生查询完成；仅切换
`AllSerchRadio` 会打开空页，不作为商品查询成功的证据。

`--play-unit-uid` 可在页面、对战或任务场景前，通过原生机库选择账号实际持有的
机体。框架先等待真实完整机体资料，再调用出击业务；必须收到原生成功回包并读回
相同 UID，才算完成换机。`--random-loadout` 使用房名中的原生 `!rand` 对战命令。

`--mission-mode 5` 或 `8` 注册任务烟雾测试：真实频道与任务选择、建房、开局、
三名等级 2 的友军刷出、移动、目标获取和原生战斗状态。场景不宣称任务通关、
结算或主动退出；缺少可进入的原生任务或频道会失败，不会补造准入数据。

`--gift-requests-only` 的私有账号配置可以用 `[gift] body0` 至 `body3` 指定服主
已有的正常邮件命令，或继续用 `page0/position0` 指定机体赠送。收件人须填写原生
角色昵称。账号权限、命令处理和发放由服务器负责；测试仍等待独立处理回执，
不会直接发币、写库存或用发送成功代替到账。凭据与命令配置保留在本地。

### 设计图合成

Python `prepare` / `reuse_prepared` API 的封存 `unit_scenario` 可传入
`schema: 1` 和 `blueprint: {recipe_id, book_uid}`，测试原生图纸列表与配方页面。
同时设置 `pages_only=True` 和已有的 `play_unit_uid`。可选的 `materials`
按配方顺序提供三到五个真实持有的 `{unit_id, uid}`；原生选机回调负责填入材料槽，
测试不会提供完整机体记录，也不直接写选择状态。
材料位于另一页机库时，测试通过原生翻页箭头等待对应缓存更新，再选择精确 UID。

仅选材料不会消耗物品。测试真实合成时，须在设计图范围中明确增加
`synthesize: true` 和 `output_unit_id`；它通过原生确认框消耗隔离账号已有的
图纸与材料，要求观察原生 `0x09AD` 请求、`0x07C9` 回包消费和匹配的产物库存简表。
另保留独立 SQL 前后读回，并通过新的原生登录验证持久化；成功回包不代表重登或获取路线闭环。
所有身份与消耗开关都在启动前绑定哈希。

### 原生目录编号占用

独立的封存机体页面范围接受
`native_id_probe: {ids: [...], witness_unit_id: ..., require_absent: true}`，
最多3072个不重复编号，范围为1–9999999。真实登录并装备后，观察器先验证已有 typed 机体见证，
再逐项调用原始全局 map 查询并检查精确 end sentinel；结果写入本轮原生诊断目录的
`native-id-occupancy.json`。该探针只读，不注册或预留编号。未占用只适用于此时这份封存客户端；
安装仍需独立冲突检查。不能与设计图、姿势、获取或扭蛋范围混用。

### 原生记录所有权与正常退出

独立封存范围 `native_record_lifecycle: {ids: [...]}` 观察测试客户端目录中的一至十六个精确编号。
它要求静音隔离的 `pages_only` 运行和已有出击实例。完成正常启动、登录和装备断言后，
测试向所属游戏窗口请求 `WM_CLOSE`，返回原始消息循环；其他套件仍沿用原来的立即退出方式。

运行器持有实际进程句柄，等待正常退出后才清理。新增报告层把原生 final-release 收据逐项对回封存目录，
原客户端的两条 final-release 返回分支分别返回退出码0或1，两者都必须有完整的原生析构收据。
核对完整记录字节、五类互不重叠的所有权地址和每个地址恰好一次释放。
即使登录用例通过，缺项、修改或重复的释放证据仍会失败。此范围只验收原始记录注册及目录析构；
技能／浮游对象的激活、战斗行为、变形、死亡和重生清理仍须单独验证。探针不新增服务端行或玩家库存。

### 多客户端协同对战

为每个不同的已有账号准备一个静音、后台的 `--friends-only` 运行目录，指向同一套隔离原生后端，
使用相同的单个 `--mode-sequence` 和 `--expected-ai`。各客户端的可写文件独立；已停止且通过的
归档基线可以提供共享只读资源包。所有客户端安装 `match_ai`，后端安装 `pvp_ai` 和被动观察器，
房主运行目录按前述方法绑定观察会话。复用已有出击机体；模式要求战舰时，账号应已有可用编队。

启动前声明全部真人驾驶员 ID。真人和 AI 共用八个原生槽位；协调器要求至少两名真人和一个 AI。
例如，三个已有账号配合 `--expected-ai 5 --ai-allies 0 --ai-teams coop --random-teams`，
会在保留房间随机队伍选项的同时，由服务端的 `coop` 规则在开局时组成三名真人对五个 AI。
将示例 ID、目录及观察流替换为已准备的测试身份和实际启用的 Battle：

```powershell
python tools/game_test_multiplayer.py --host-run build/cohort/host --peer-run build/cohort/peer1 --peer-run build/cohort/peer2 --human-pilots 101,102,103 --server-events D:\SDGO-Test\server\Server\BattleServer4\sdgo\gametest\server-observer-events.jsonl --output build/cohort-result.json
```

房主先真实建房。客人切换到房主实际所在频道，按完整的服务端房名找到房间，调用原版入房业务。
Ready 走原版三维房间 Main 业务及玩家状态机：必须观察到真实请求、原版回包处理完成和当前房间
模型更新，协调器才允许房主开局，不直接设置 Ready 标志或补入房间成员。

战斗中分别核对房主的本地 AI 控制权、客人的远端同步副本、真实移动及房主的战斗证据，之后等待
原生结算返回同一间真人持有的房间。客人先离房、房主最后离房；每次退出都显式绑定实际观察到的
频道和房间 ID，调用原生业务。独立服务端报告另行核对预先声明的真人名单、AI 队伍和完整战斗
生命周期。启动、战斗或退出失败都会使整轮失败，并且只中止所属客户端。账号、凭据、端点和
报告继续留在本地；这是开发用测试命令，不是玩家启动器。

服务端被动验证使用 `tools/game_test_server_report.py --run-dir build/gametest/pvp
--events <server-observer-events.jsonl> --host-pilot <角色ID>`。矩阵使用多个 Battle
主机时重复传入 `--events`。每个模式都必须具备同次运行、相同房名与角色、正确
队伍和完整四阶段原生生命周期，结果写入 `receipts/server-report.json`。
单场服务端摘要不能代替整个客户端矩阵的验证。

两个组件均作为开发类 Mod 接入 Mod Manager。Python 运行器是执行有限测试任务的
开发命令，不是玩家启动器或常驻服务。账号配置和运行回执不得放入分发包或源码仓库。

开发者明确需要可见录制时，`prepare` 加 `--visible --sfx-only`，构建 `game_test_audio` 目标，再运行
`python tools/game_test_record.py --run-dir build/gametest/pvp --output D:\Videos\SDGO-GameTest`。
仅测试副本关闭 BGM、启用音效。每场通过开局和 AI 断言后录制最多 25 秒，画面和声音
只取自该测试游戏进程。失败、静音或黑屏片段会清理；保留素材仍需检查交战情况与构图，
AI 断言通过本身不代表画面适合剪辑。

使用 `--room-titles-only` 可在真实登录后检查普通、AI、队伍和任务建房，以及当前三维等候室中可用的房内改名。
每个窗口通过实际原生编辑器输入 21 个键盘字符、
超过 20 字符的中文和 128 字符标题，再验证取消重开与服务端确认的完整文本。
中英文字符通过实际 Win32 EDIT 的 `WM_CHAR` 消息队列输入，让原生 IME 过滤器处理后，再读回游戏自己的编辑框文本；测试不使用文字赋值函数。
若原生好友聊天窗口延迟初始化并清空共用输入框，测试记录该原生调用，取消重开房名窗口后重新执行全部断言，最多重开两次。
测试观察器不修改输入上限；系统输入法候选窗和剪贴板不在此场景范围内。
当前客户端建房成功进入原生三维等候室；队伍视图保留原来的改名权限条件。
二进制中仍包含旧式二维队伍/协作设置窗口，但现代会话没有进入它们的正常路径，因此只做 C++、原生布局和协议回归。
内联改名框没有确认按钮。测试向其已核对的原生输入查询提供一次 Enter 或 Esc，随后仍由原生窗口处理、构包并等待真实服务器确认；其他窗口和按键查询不变。
复用本地原生 test 后端，使用 `prepare --room-titles-only --include-mod room_titles`，
明确指定测试回环地址、登录端口和已有账号配置，再使用 `run --timeout 1200`。
后续迭代使用停止的所属客户端及 `--reuse-client`，不重新还原数据库。
场景通过原生换机流程选择该账号已有的默认机体；配套服务端候选只安装到所属停止的 Agent/Battle 副本，
保留原有配置、合并符号并核对文件哈希。输入矩阵通过原生离房流程退出各个房间。
最后重新创建长房名 AI 房，验证真实开战回包和原生 `GAME_MAIN`，以及完整标题仍被保留；
此开战检查不覆盖战斗表现、结算或自然返回，结束时由运行器退出所属测试客户端。
完整运行要求后端已启用配套长房名
Agent/Battle Mod；窗口输入通过与服务端标题确认分别断言。测试账号配置和回执继续留在本地，不进入玩家分发包。

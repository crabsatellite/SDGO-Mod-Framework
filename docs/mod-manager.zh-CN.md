# 统一 Mod Manager

[English](mod-manager.md) · [返回功能目录](../README.zh-CN.md)

Manager 统一管理客户端更新、Mod 配置和服主工具。玩家使用服主提供的客户端包或更新；带有完整客户端来源的安装会直接打开更新页。
共享 Mod 和内容配置由服主维护，游戏仍从原来的入口启动。

可以从客户端目录顶部的 **0_更新与管理**，或包里的 **SDGO Mod Manager.exe** 打开 Manager。
第一次正常打开时会创建目录入口；入口丢失时，点击提示栏的「创建目录入口」补建，已有入口及其工作区保持不变。
Manager 不会在桌面创建快捷方式。

所有管理功能共用一个本机界面，不需要安装 Python，也不需要分别启动商城、奖励、副官或扭蛋机的单独程序。

游戏中的操作仍在对应游戏页面完成，例如机库整理和重复兑换位于「机体管理」页；Manager 只调整其偏好与安装状态。

界面里的机体插画和机库纹理在运行时从你选择的客户端读取，仓库与发行包不附带游戏美术；没有客户端时界面保持自绘外观。

## 日常管理

默认界面面向玩家和服主。用顶部的「添加目录」加入客户端或服务器目录，再从「管理对象」选择要管理的目录。
「添加目录」和设置里的「浏览…」打开 Windows 的文件夹 / 文件选择窗口；窗口打不开时，改为显示手动填写路径的输入框。
新加入的目录由 Manager 自动安装框架，装好后页面自动列出可管理的功能。
「游戏功能」里每个功能只显示名称、一句说明和开关；有可调参数的功能显示「设置」，其余显示「说明」。
修改后重新启动对应游戏或服务器生效。客户端可以导入服主给的配置包；需要一次关闭整类功能时，用页面底部的「批量开关」。
功能详情页底部的「遇到问题？」可以复制给 AI 排查或整理 Bug 报告。

只管理客户端时，左侧只显示「游戏功能」和「修复归档」。加入任一服务器目录后（或点击「我是服主：显示服主工具」），
左侧出现「服主工具」：商城、副官、机体导入、扭蛋机、战斗奖励、FRP、AI 机体清单、收藏扭蛋、机库服务端、[节日与生日赠礼](calendar-gifts.zh-CN.md)和后台任务。首次使用时选择现有配置和游戏目录，
保留已创建的商品、副官、扭蛋机、历史记录和队列。不同服务器的数据工作区应明确选择，不会按相同库名合并。

商城先保存草稿再应用；副官沿用原有外观、掉落和发放校验；扭蛋机保留固定槽位、自定义池、价格和模板。
商城的名称、说明和销售选项可使用独立的[商城中文汉化 Mod](shop-localization.zh-CN.md)。
新增商品必须填中文名，中文销售标签按租期/数量生成；导入和发布同样校验。
「导出玩家更新包」包含配套商城模块和显示数据，玩家导入 Manager 后照常用原启动器。
奖励工作器和商城业务通道由 Manager 的统一任务注册表管理，关闭浏览器标签不会停止服务。
“后台任务”页统一显示启停、健康状态和自动恢复设置。已启用任务会在 Manager 下次启动时恢复，
异常退出的任务由 Manager 负责重试。更换奖励服务器或工作目录前先停止对应任务。
这些操作不负责原生游戏服务器进程的启停。

FRP 使用服主自己的端点设置，导出的玩家包只包含客户端连接配置。玩家导入后仍用原启动器。
AI 清单支持检查、生成配套数据、安装到已停止的目标和导出玩家包；更新时保留原编号分配记录。

「机体导入」支持 RAR/ZIP 解析、必填项补齐、商城和扭蛋两种图片的预览确认及双端发布。
确认只登记定义和展示资源；机体获取需要在商城上架，或同步到扭蛋目录后配置机台并应用。
玩家通过普通客户端配置包导入入口安装配套机体资源。发行包不携带服主机体内容；详见[机体导入指南](unit-import.zh-CN.md)。

界面分别显示已保存、已安装和需要重启；保存成功后，按提示重启对应游戏或服务器才会加载新设置。
导入会替换文件的包之前，先关闭目标游戏。

保存和生效的规则在界面上都写明了：

- 「游戏功能」卡片上的开关点一下就立即保存，不需要再按保存；重启对应游戏或服务器后生效。
- 「设置」页和需要手动保存的工具页，底部有一条始终可见的保存栏，显示哪些修改还没保存，并提供「保存」和「放弃修改」。
  每个设置旁标明「重启后生效」或「即时生效」。有未保存的修改时离开页面，会先询问。
- 节日与生日赠礼分「通用规则」和「本服私人名单」两部分保存，每个区块写明归哪一部分，
  「保存全部并重启后台任务」一次保存两部分并重启后台任务。
- 战斗奖励的各部分用各自区块里的按钮分别保存，每个区块标题下写明它保存什么、只读试算的区块不会保存；
  底部保存栏列出哪些部分还没保存，点名称可跳过去。保存任一部分后整页按已保存的配置刷新，
  所以另一部分还有未保存的修改时会先询问。
- FRP 页的「保存配置」和「导出玩家配置包（先保存）」在底部保存栏；收藏扭蛋按编号步骤生成、检查、安装和导出。
- 保存结果在窗口右下角提示，滚动到页面任何位置都能看到；出错的提示会一直保留，直到手动关闭。
- 较长的页面在标题下方列出「本页」各区块，点击直接跳转；向下滚动后可以「回到顶部」。
- 扭蛋机的机台列表和编辑区分别滚动，编辑区顶部的「保存配置」和底部的导出、「导入到游戏」始终可见。

左侧「收藏扭蛋」负责生成配套资源、分别安装 World 和客户端、导出玩家包以及登记多形态内容，详见
[收藏扭蛋教程](collection-capsule.zh-CN.md)。

## 依赖、数据与生效状态

Manager 在开关、分类开关、设置保存和运行包安装前检查必需依赖、可选接口、冲突与循环加载关系。
必需依赖需要已安装并启用；可选依赖允许缺席，但同时启用时必须满足声明的版本和接口要求。
已安装机体、副官或扭蛋内容仍需要对应运行时。禁用或退役这些运行时之前，先处理内容与获取途径；已有玩家资产不会随开关自动删除。
已知旧版目录也会获得这些保护，不需要改写其历史记录或重新分配编号。

升级 Manager 或框架本身不迁移数据库、不重置开关，也不清除已有内容。
机体定义、扭蛋目录、副官应用及收藏扭蛋规则升级等显式操作会先列出数据影响，再确认提交。
固定目录写入需要停止所选服务组，并使用支持维护回执的配套框架；Manager 不会代替服主结束原生服务。
无法核实远程数据库的全部原生服务时，应在服务器所在机器执行维护。

保存、提交与运行生效分别显示。支持热重载的组件需要确认读入同一版配置，才能显示已生效；其他设置等待下一次启动。
固定目录提交后，需要核对新进程、监听和本次原生表加载完成。新内容在确认前不会自动加入新的获取途径。
旧内容没有新回执时保持既有状态；中断或未完成的变更会保留恢复记录，不能当作已经回滚或生效。

## 更新

### 完整客户端

服主提供的客户端包或更新可携带 `sdgo/client-source.json`。双源安装将框架／Mod 程序来源和服主内容来源分别绑定，两者都支持 Git SSH／HTTPS 镜像，并复用已有 Git 身份与 SSH 配置。

框架源提供 Manager、核心、Mod 程序、接口声明和默认配置；服主源提供原版客户端资源、新增机体、模型贴图、生成目录及共享参数。内容清单声明最低框架版本与必需 Mod。框架运行包使用与 Release 相同的 ZIP、版本和摘要，通过专用 Git 运行分支分发，源码镜像本身不能代替运行包。

在「完整客户端更新」检查两层差异并确认安装。Manager 先下载、校验并检查兼容性，再使用一次事务安装，失败整体回滚；一个来源不可用时保留当前安装。运行文件与归档分段下载失败会继续尝试同身份的后续镜像。Manager 自身替换通过正常重启交接完成，游戏运行时等待关闭。

共享配置跟随服主发布，包括声明的配置文件、脚本和 Mod 参数，不会因本地已有旧值而跳过。个人登录、画面／FPS 设置、显式登记的个人参数、仅本地 Mod 和未退役的额外自定义文件保留。回执分别记录框架版本、框架提交和内容提交。框架升级不迁移服务器数据库。

独立 Manager 可在程序来源中配置 Git 框架源。绑定双源客户端的 Manager 通过统一事务更新。新程序写到磁盘仍需重启才能成为当前运行版本，界面不会把待重启报告成「最新」。

### 框架与 Mod 发布

左侧的「更新」按钮提供两个通道：

- **只更新 Stable（默认）**：仅安装正式发布的 Stable 功能。
- **更新 Beta 功能**：同时安装 Stable 与 Beta 功能，跟进最新可用版本。

两种通道都不安装开发诊断类功能。切回 Stable 不会删除已安装的 Beta 或自定义 Mod，只更新 Stable 包中的功能。
通道与自动更新开关保存在当前 Manager 工作区，新安装默认 Stable。

Manager 运行时默认在启动后及每小时自动检查。可用「检查更新」立即检查、「立即更新」安装已发现版本，也可关闭自动更新继续手动检查。程序上游默认为本项目 GitHub Releases，可在本页改为兼容的 GitHub `owner/repository`。HTTPS 证书由 Windows 自己校验，和浏览器一致；先校验发布身份、SHA-256 和完整清单，再安装。断网时保留已安装版本，恢复网络后可重试。

每个已登记目录单独选择维护方式：「基础整合包」接受上游运行更新，「服主 DIY」保护现有运行文件、只采用审阅确认的组件，「玩家」只跟随绑定服主的整合包。没有明确维护选择的目录默认跟随基础整合包，已有 Mod 安装也使用这一默认值。服主需要自行维护时，明确选择并保存 DIY 模式；已有明确 DIY 选择、发布设置和玩家绑定会保留。程序更新不会自动覆盖 DIY 或玩家目录。官方整合包提供一套基础搭配；DIY 后的配置、脚本、素材、兼容性与发布版本由服主负责。发布、玩家绑定及私有 Git 访问见[服主整合包更新](owner-updates.zh-CN.md)。

正在运行的游戏或服务不会被停止，运行文件更新等待其关闭后安装。上游更新保留 Mod 开关、已有参数、独立配置文件、自定义 Mod、机体资源与私人数据；DIY 中明确选中的程序／脚本组件采用上游文件，应先查看差异。文件写入失败时回滚对应目录，恢复副本位于本地 Manager 工作区。

本地安装的 Mod 版本高于发布包时，保留该 Mod 及其所需的原生符号配置，不会被降级。

管理器本身有更新时，点击「重启 Manager 完成更新」。新程序等待旧 Manager 正常退出，校验并替换程序，再打开相同工作区；普通 Mod 更新无需重启 Manager。

更新时同时核对机体内容的安装收据：只更新程序组件对应的记录，保留机体记录、模型、贴图、获取配置和安装身份；内容被改动时拒绝提交，校验失败会恢复本次写入。

可配置的时区默认取服务器本地时区。更新页的「时间显示」留空时跟随服务器本地，也可只为当前 Manager 填写 UTC 偏移分钟；这不会修改 Windows 系统时区。

## 归档与开发信息

输入法、启动崩溃、中继日志和军衔回退等自动修复，只在“修复归档”查看，标记为“自动生效”。新账号初始内容属于日常管理，
不会因为旧分类叫 fixes 就藏起来。

“显示开发信息”展开内部代号、版本号、诊断开关和开发设置，并允许临时关闭自动修复。管理服务器、添加内容、调整规则不要求进入开发视图。

## 给 AI 的入口

每个功能都有“复制给 AI 配置 / 调试”和“发现 Bug，复制给 AI 报告”。可粘给 DeepSeek 或其他 AI：

- 配置说明整理该功能的原理、实际位置、地址、已登记参数和当前状态；不读取或复制数据库密码和令牌。
- Bug 说明指向 [GitHub 仓库](https://github.com/crabsatellite/SDGO-Mod-Framework)，要求先查重复 issue，再根据真实复现报告。
- 用户愿意尝试修复时，引导读源码、配置开发环境、建分支、测试和提交 PR。
- PR 必须披露实际模型名称/版本、AI 参与范围、人工核对和未验证项。型号未披露时写未知，不猜测。

Bug 报告说明不附带本机绝对路径或端点。不要自行粘入凭据、真实账号、私有快照或游戏资源。
开发环境和 PR 规范见[贡献说明](contributing.zh-CN.md)。

## 开发与注册

每个 Mod 的 `manager.json` 声明日常/开发字段、存储位置、范围和生效方式；复杂编辑功能通过 Provider 注册。
框架共用会话校验、配置版本检查、原子保存、目录边界、面板与下载。注册文件会随 Mod 一起分发。
长期工作器通过 `workspace.services.register` 登记，内部 IPC 通道通过同一注册表申请和释放。
模块不创建独立的管理服务或入口；商城配置只由 Manager 发布，WorldServer 启动时不会自动应用。

```powershell
python -m pip install -r manager/requirements-build.txt
powershell -ExecutionPolicy Bypass -File tools/build_mod_manager.ps1
```

构建的 EXE 包含内部业务库和所需运行时。游戏运行库继续独立加载，Manager 不替代原游戏启动器。
源代码版本也可用 `python tools/mod_manager.py` 调试。开发设计见[注册和迁移设计](mod-manager-design.zh-CN.md)。

### 构建发布包

发布者使用 `python tools/build_release.py --build --channel stable --version X.Y.Z` 构建 Stable，或 `--channel beta --version X.Y.Z-beta.N` 构建 Beta。包里只有 Manager 与登记的框架文件，不含原版客户端、服务端、数据库、测试副本或账号配置。发布工作流先验证更新安装、构建对应代码并检查 Manager 成品；master 后续提交自动生成 Beta release，正式版本标签生成 Stable release。

### 仅本地 Mod

统一放在客户端的 `sdgo/local-mods/<id>/` 中。加载器和 Manager 都会发现该目录，
Manager 导入标记为仅本地的配置包时也会自动选择它。整个 `sdgo/local-mods/` 应由
版本管理忽略，公开打包、导出和源码分发检查会拒绝包含该目录的内容；新增私人扩展无需逐个添加排除项。
这些检查按 Windows 路径规则忽略保留目录名与清单文件名的大小写，改动字母大小写不能绕过分发限制。

服主个人使用的 Mod 保存在独立私有仓库中。它在 `mod.ini` 的 `[mod]` 中声明
`distribution=local_only`，在 `manager.json` 顶层声明
`"distribution": "local_only"`；仓库根目录的 `distribution.json` 声明
`{"distribution":"local_only","redistributable":false}`；每个私有 `.cpp`/`.h`
文件首行带框架约定的仅本地源码标记，运行 DLL 嵌入框架约定的禁止分发标记。
Manager 可以把它安装到服主选定的客户端、显示“仅本地 · 禁止导出”并管理配置，
但不会把它视为可导出的公共内容。

公共仓库随包 Mod 必须在两份清单中都明确声明 `public`。
`tools/distribution_guard.py` 可检查待提交索引、指定提交、整个待推送 Git 历史范围、
源码工作树、输出目录和 ZIP；即使私有文件在较早提交加入、最终提交又删除，也会被拦截。
catalog 生成器、冻结 Manager 构建、Manager 下载响应、通用打包、Release 构建和更新包读取
还会重复校验。改名 DLL 或删除某一份清单不能把仅本地内容变成可发布内容。

```powershell
python tools/distribution_guard.py --git-index
python tools/distribution_guard.py --git-tree HEAD
python tools/distribution_guard.py --git-range origin/master..HEAD
python tools/distribution_guard.py --source-path .
python tools/distribution_guard.py --path build\public-package
python tools/distribution_guard.py --archive dist\SDGO-ModFramework-X.Y.Z.zip
```

较老的客户端仓库若公共 Mod 还没有分发字段，Git hook 可加
`--allow-legacy-public`。它只兼容“两份声明都缺失”的旧公共清单，仍会拒绝
`local_only`、单边声明、仓库/源码标记和带禁止分发标记的二进制。公共框架源码、
Manager 构建和发布包仍使用上面的严格命令。

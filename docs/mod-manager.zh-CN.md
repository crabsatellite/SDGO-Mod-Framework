# 统一 Mod Manager

[English](mod-manager.md) · [返回功能目录](../README.zh-CN.md)

这是**服主与维护人员工具**。普通玩家应使用游戏启动器，并遵循服主提供的安装和更新方式，不要自行调整 Mod；客户端 Mod 与服务器配置不匹配，可能导致无法进入游戏、断线或崩溃。管理器每个页面顶部都会显示这一提示。

服主可通过客户端目录顶部的 **0_MOD管理（服主专用）**，或包里的 **SDGO Mod Manager.exe** 打开管理器。首次正常打开会创建目录入口，也可点击提示栏的「创建目录入口」补建；已有可用入口及其工作区保留。不会在桌面新建快捷方式。程序、目录入口和网页标签统一使用左上角的 SDGO 标志。所有管理功能共用一个本机界面，不需要安装 Python，
也不再分别启动商城 EXE、奖励网页、副官助手或扭蛋机编辑器。

游戏中的操作仍在对应游戏页面完成，例如机库整理和重复兑换位于「机体管理」页；Manager 只调整其偏好与安装状态。

界面里的机体插画和机库纹理在运行时从你选择的客户端读取，仓库与发行包不附带游戏美术；没有客户端时界面保持自绘外观。

## 日常管理

默认界面面向玩家和服主。用顶部的「添加目录」加入客户端或服务器目录，再从「管理对象」选择要管理的目录。
「游戏功能」里每个功能只显示名称、一句说明和开关；有可调参数的功能显示「设置」，其余显示「说明」。
修改后重新启动对应游戏或服务器生效。客户端可以导入服主给的配置包；需要一次关闭整类功能时，用页面底部的「批量开关」。
功能详情页底部的「遇到问题？」可以复制给 AI 排查或整理 Bug 报告。

只管理客户端时，左侧只显示「游戏功能」和「修复归档」。加入任一服务器目录后（或点击「我是服主：显示服主工具」），
左侧出现「服主工具」：商城、副官、机体导入、扭蛋机、战斗奖励、FRP、AI 机体清单、收藏扭蛋、机库服务端、[节日与生日赠礼](calendar-gifts.zh-CN.md)和后台任务。首次使用时选择现有配置和游戏目录，
保留已创建的商品、副官、扭蛋机、历史记录和队列。不同服务器的数据工作区应明确选择，不会按相同库名合并。

商城先保存草稿再应用；副官沿用原有外观、掉落和发放校验；扭蛋机保留固定槽位、自定义池、价格和模板。
商城的名称、说明和销售选项可使用独立的[商城中文汉化 Mod](shop-localization.zh-CN.md)。
新增商品必须填中文名，中文销售标签按租期/数量生成；导入和发布同样校验。
「导出玩家更新包」包含配套商城模块和显示数据，朋友导入 Manager 后仍用原启动器。
奖励工作器和商城业务通道由 Manager 的统一任务注册表管理，关闭浏览器标签不会停止服务。
“后台任务”页统一显示启停、健康状态和自动恢复设置。已启用任务会在 Manager 下次启动时恢复，
异常退出的任务由 Manager 负责重试。更换奖励服务器或工作目录前先停止对应任务。
这些操作不负责原生游戏服务器进程的启停。

FRP 使用服主自己的端点设置，导出的玩家包只包含客户端连接配置。玩家导入后仍用原启动器。
AI 清单支持检查、生成配套数据、安装到已停止的目标和导出玩家包；更新时保留原编号分配记录。

「机体导入」支持 RAR/ZIP 解析、必填项补齐、商城和扭蛋两种图片的预览确认及双端发布。
确认只登记定义和展示资源；机体获取需要在商城上架，或同步到扭蛋目录后配置机台并应用。
玩家通过普通客户端配置包导入入口安装配套机体资源。发行包不携带服主机体内容；详见[机体导入指南](unit-import.zh-CN.md)。

保存、安装、需要重启和实际运行确认是不同状态。界面不因保存成功就宣称游戏已经加载。
目标游戏正在运行时，关闭该副本再导入会替换文件的包。

左侧「收藏扭蛋」负责生成配套资源、分别安装 World 和客户端、导出玩家包以及登记多形态内容，详见
[收藏扭蛋教程](collection-capsule.zh-CN.md)。

## 归档与开发信息

输入法、启动崩溃、中继日志和军衔回退等自动修复，只在“修复归档”查看，标记为“自动生效”。新账号初始内容属于日常管理，
不会因为旧分类叫 fixes 就藏起来。

“显示开发信息”展开内部代号、版本号、诊断开关和开发设置，并允许临时关闭自动修复。管理服务器、添加内容、调整规则不要求进入开发视图。

## 给 AI 的入口

每个功能都有“复制给 AI 配置 / 调试”和“发现 Bug，复制给 AI 报告”。可粘给 DeepSeek 或其他 AI：

- 配置说明整理该功能的原理、实际位置、地址、已登记参数和当前状态；不读取或复制数据库密码和令牌。
- Bug 说明指向 [GitHub 仓库](https://github.com/crabsatellite/SDGO-Mod-Framework)，要求先查重复 issue，再根据真实复现报告。
- 用户愿意尝试修复时，引导读源码、配置开发环境、建分支、测试和提交 PR。
- PR 必须披露实际模型名称/版本、AI 参与范围、人工核对和未验证项。型号未披露时写未知，不猜测。

Bug 报告说明不附带本机绝对路径或端点。不要自行粘入凭据、真实账号、私有快照或游戏资源。
开发环境和 PR 规范见[贡献说明](contributing.zh-CN.md)。

## 开发与注册

每个 Mod 的 `manager.json` 声明日常/开发字段、存储位置、范围和生效方式；复杂编辑功能通过 Provider 注册。
框架共用会话校验、配置版本检查、原子保存、目录边界、面板与下载。注册文件会随 Mod 一起分发。
长期工作器通过 `workspace.services.register` 登记，内部 IPC 通道通过同一注册表申请和释放。
模块不得再创建独立管理服务或自行恢复旧入口；商城 WorldServer 启动自动应用已移除，配置仅由 Manager 发布。

```powershell
python -m pip install -r manager/requirements-build.txt
powershell -ExecutionPolicy Bypass -File tools/build_mod_manager.ps1
```

构建的 EXE 包含内部业务库和所需运行时。游戏运行库继续独立加载，Manager 不替代原游戏启动器。
源代码版本也可用 `python tools/mod_manager.py` 调试。开发设计见[注册和迁移设计](mod-manager-design.zh-CN.md)。

## 更新

左侧的「更新」按钮提供两个通道：

- **只更新 Stable（默认）**：仅安装正式发布的 Stable 功能。
- **更新 Beta 功能**：同时安装 Stable 与 Beta 功能，跟进最新可用版本。

两种通道都不安装开发诊断工具。切回 Stable 不会删除已经安装的 Beta 或自定义 Mod，只更新 Stable 包包含的功能。通道与自动更新开关保存在当前 Manager 工作区，新安装默认 Stable。

Manager 运行时默认在启动后及每小时自动检查并安装。可用「检查更新」立即检查、「立即更新」安装已发现版本，也可关闭自动更新继续手动检查。下载来源为本项目 GitHub Releases；先校验 release 文件 SHA-256 和完整清单，再安装。断网时保留已安装版本，恢复网络后可重试。

更新对象为已登记的客户端和服务器目录。正在运行的游戏或服务不会被停止，下载完成后等待其关闭再自动安装。保留 Mod 开关、已有参数、独立配置文件、自定义 Mod、机体资源与私人数据；文件写入失败时回滚对应目录，恢复副本位于本地 Manager 工作区。

本地 Mod 的版本高于发布包时，保留该 Mod 及其所需的原生符号配置，避免并发开发时降级已有的新版本。

管理器本身有更新时，点击「重启 Manager 完成更新」。新程序等待旧 Manager 正常退出，校验并替换程序，再打开相同工作区；普通 Mod 更新无需重启 Manager。

发布者使用 `python tools/build_release.py --build --channel stable --version X.Y.Z` 构建 Stable，或 `--channel beta --version X.Y.Z-beta.N` 构建 Beta。包里只有 Manager 与登记的框架文件，不含原版客户端、服务端、数据库、测试副本或账号配置。发布工作流先验证更新安装、构建对应代码并检查 Manager 成品；master 后续提交自动生成 Beta release，正式版本标签生成 Stable release。

# 机库整理与重复机体兑换

[English](hangar-manager.md) · [返回功能目录](../README.zh-CN.md)

客户端 Mod `hangar_manager` 在游戏「机体管理」页的「机体锁定/解除」「机体解体」旁增加「一键整理」和「重复兑换」按钮。
操作全部在原游戏页内完成，没有独立窗口、悬浮工具条或热键，也不要求 Manager 常驻。
整理和 GB 批量回收由服务端执行，服主需要先安装服务端通道。

## 一键整理

服务端按 S/A/B/C、子等级、机体编号、获得时间及实例编号排序全部机体，只更新槽位。锁定状态、出击机体、
舰队、培养及其他机体数据保持不变，不会解锁或撤下舰队。整理时还会核对机库容量，必要时按六格档位补到能容纳
现有机体的最小值，最多 1200 格（旧脚本导入机体后若没有同步容量，超过 `24 + ExpandSlotCount` 的记录会让原生登录
槽位写入越界）。

提交后显示“已提交服务器”，**退出并重新登录**后查看排序结果。

## 重复兑换

- 按机体编号统计，每种默认至少保留两台（`KeepCopies`，1–20），受保护的副本也计入保留数量。不同涂装按同型号计数，
  想保留的机体请先锁定。
- 锁定、出击、舰队、租赁及已培养的机体不会被兑换。已安装 `unit_catalog` 导入的机体会按原生等级自动补入规则；
  找不到唯一奖励规则或规则有冲突的等级仍会跳过。
- 可选择原生 GB 或原生道具奖励（通常为经验胶囊），最终奖励以服务器的 `tbl_UnitGradeInfo` 和原生拆解过程为准。
- 预览和第一次确认不会删除机体，需要两次确认。离开该页会取消预览。

**GB 回收**直接用原生机库摘要生成清单，确认后把选中的精确实例、机体编号和槽位交给服务端，一次事务内重新检查
归属、保护状态、保留数量和奖励，调用原生拆解并入账 GB。清单不完整、数据已变化或任何一笔失败都整体不执行，
不会部分扣机体或部分发钱；重复提交也不会重复入账。提交后重新登录查看。

**道具回收**沿用原生逐台流程：逐台确认后才发下一笔，无法确认回包、连接变化或机库被其他操作修改时停止，不自动重试；
已经确认的操作不会回滚，状态不明时重新登录后再操作。

离开机体管理页会取消尚未确认的预览，恢复原生按钮；重新打开时从预览重新开始。

## 安装

**服务端：** 在 SDGO Mod Manager 左侧打开「机库整理与批量回收服务端」，选择含 `DB Game`、`DB Member` 的服务器 INI
（两个数据库需在同一 SQL 实例），点击安装或更新。安装会备份原生邮件过程并保留普通邮件路径，只有专用命令进入排序和
回收逻辑；同一次安装还会加入机体删除防护：一条 SQL `DELETE` 语句只能删除一个账号的机体。所有允许的删除都会把机体
原始完整行、UTC 时间及受限长度的 SQL 会话／应用／主机信息写入专用审计表。Manager 只显示防护状态和审计行数，不显示
玩家记录；移除服务端通道时保留审计历史。面板可检查已安装过程及触发器的哈希，也可移除通道并恢复原邮件过程。不需要
重启游戏服务器。

**客户端：** 玩家通过服主提供的客户端包或更新获得。完整框架包中已包含本 Mod（Base 包不含）；也可以用 Manager 的
「导入配置包」导入本 Mod 的增量包，或关闭目标客户端后运行独立包中的：

```powershell
powershell -ExecutionPolicy Bypass -File install_hangar.ps1 -GameDir "D:\Games\SDGO"
```

增量安装只更新 `hangar_manager` 和它的符号节，保留已有核心、全局设置、其他 Mod 和已有设置；`-RefreshRules` 会更新
奖励预览规则。支持的客户端为 `GOnline-54BE1568-00C97000`，不匹配的版本拒绝安装。

## 设置

在 SDGO Mod Manager 的「机库整理与回收」中调整“至少保留机体份数”和“回收后整理机库”。其余为开发设置，
点“显示开发信息”后显示。配置位于 `sdgo/mods/hangar_manager/mod.ini`：

| 设置 | 默认值 | 含义 |
|---|---|---|
| `KeepCopies` | 2 | 每种机体至少保留的数量 |
| `SortAfterExchange` | 1 | 兑换后整理可移动机体 |
| `RequestIntervalMs` | 150 | 原生请求最小间隔（开发） |
| `ReplyTimeoutMs` | 10000 | 等待数据同步的最长时间（开发） |
| `MaxSlots` | 1200 | 可移动槽位上限（开发） |
| `RulesFile` | units.tsv | 相对本 Mod 目录的机体/奖励预览表（开发） |

规则文件只决定显示和客户端筛选，不能提高服务器发放的奖励，其中明确写出的机体编号优先。客户端启动时会验证已安装的
`unit_catalog/catalog.bin`，再把缺失的导入机体按其已验证的原生等级匹配到本表中唯一一致的奖励规则。目录损坏时不补入，
同一等级存在互相冲突的奖励规则时也不会猜测。服务器规则变更后，服主可只读导出基础规则：

```powershell
python export_hangar_rules.py --server-ini "D:\Server\StoreServer.ini" --output units.tsv
```

该工具需要 SQL ODBC 驱动和 `pyodbc`，也可用 `--snapshot` 读取配置表 JSON；只查询机体、等级奖励和奖励名称配置。
玩家运行 Mod 不需要 Python。

## 开发者说明

- 整理和 GB 批量请求借用原生邮件发送 `0x0891`（345 字节），服务端从自身账号上下文派生归属，玩家不传入目标账号。
  原生邮件路径没有整理完成回执，因此客户端只显示“已提交服务器”；服务端完成后写入独立回执表，由 Manager 读回。
- 排序事务只改 `tbl_UserUnits.UserUnitSlotNumber`，按旧排序脚本的顺序生成槽位，再逐列核对其他机体数据。
- 删除触发器会检查整条语句的 `deleted` 集合；只要同时出现两个 `AccountNumber` 就拒绝并回滚。审计写入与调用者使用
  同一事务，因此原生操作失败或外层事务回滚时，不会留下错误的审计记录。审计不保存 SQL 文本或凭据。
- 道具回收使用原生拆解 `0x06D2`（19 字节，奖励选择 1 为 GB、2 为道具）和详情 `0x078B`（14 字节），服务端再次检查
  所属、锁定、出击和舰队状态。原生协议使用稳定的 `UserUnitNumber`，不按“第几个格子”猜测机体。
- 预览与执行之间再次校验实例编号、槽位、保护状态和状态指纹；按钮使用旁边原生按钮的皮肤和文字样式，全部控件初始化
  完成后才显示，失败时不拦截原有锁定/解体操作。

构建与测试：

```powershell
cmake -S . -B build/hangar -G "Visual Studio 17 2022" -A Win32
cmake --build build/hangar --config Release
ctest --test-dir build/hangar -C Release --output-on-failure
```

原生鼠标回放需配置 `-DSDGO_HANGAR_NATIVE_HOST="D:/Games/SDGO/GOnline.exe"`，构建 `hangar_native_input_test` 后运行
`ctest --test-dir build/hangar -C Release -R hangar_native_input_replay --output-on-failure`。
